# ГеоRAG · как устроено

> Как поставить и запустить — **`ЗАПУСК.md`** в корне проекта. Команды — **`КОМАНДЫ.md`**
> рядом. Этот файл — про устройство.

Путь статьи: тема → поиск в источниках → отбор → разбор PDF → фрагменты с номерами
страниц → векторы и полнотекстовый индекс в PostgreSQL → поиск, чат-бот, граф связей.

## Запуск

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
```

Добыча по теме — статьи находятся, фильтруются и разбираются сами:

```bash
python -m georag.acquire.cli "выделение рудных узлов" --device cuda
python -m georag.acquire.cli "выделение рудных узлов" --dry-run        # только поиск и фильтрация
python -m georag.acquire.cli "рудные узлы" --no-llm --queries 1        # без модели, проверка обвязки
```

Парсинг папки с готовыми PDF — когда статьи уже лежат на диске:

```bash
python -m georag.parse.cli --input .local/pdf --device cuda
python -m georag.parse.cli --input .local/pdf/one.pdf --no-chunks   # быстрая проверка парсинга
```

## Этап добычи

Порядок шагов — из части 10 плана, и LLM участвует ровно в двух местах из пяти:
она формулирует поисковые запросы и решает по аннотации, относится ли статья к теме.
Что скачивать, что сохранять и куда — решает код.

```
тема → запросы (LLM) → поиск по каталогу источников → фильтрация аннотаций (LLM)
     → получение статьи в память → парсинг → валидация → чанкинг → ссылка и текст на диск
```

**PDF не сохраняется.** Отдельного шага «скачать файл» в пайплайне нет: статья приходит
в память, сразу разбирается, и на диск ложится результат. Оба парсера это умеют —
у docling есть `DocumentStream`, у PyMuPDF — открытие из потока байт.

Вместо PDF в `.local/acquired/` остаётся:

`<doc_id>.json` — ссылка на статью, метаданные, отчёт валидации и `sha256` полученных
байт с временем получения. Хэш нужен ровно для одного: позже увидеть, что файл
на сайте подменился или исчез, — самого файла у нас нет.

`<doc_id>.docling.json` — структурный документ. Это замена хранению PDF: из него
перечанковывается без выхода в сеть, если поменяются настройки чанкинга.

`<doc_id>.md` и `<doc_id>.chunks.json` — текст и фрагменты с номерами страниц.

**Формулы** (`Settings.formulas`, по умолчанию включено). Docling находит формулу на
странице, но без отдельной модели не читает её: вместо формулы — заглушка
`<!-- formula-not-decoded -->`, которую чистка (`index/noise.py`) убирает, и формула
молча пропадает. В нашей базе так потеряно 265 формул в 43 статьях из 106: в тексте
«вычисляется по следующей формуле:» — и дальше ничего. Теперь формулы распознаёт
модель CodeFormulaV2 (0,64 ГБ, скачивается сама при первом разборе) и кладёт во
фрагмент LaTeX: `$$S_w = \left( \frac{a R_w}{\varphi^m R_t} \right)^{1/n}$$` — его
читают и поиск, и Qwen.

Проверка — на собранном для этого PDF настоящей вёрстки: дроби с чертой, суммы,
интегралы, корни, матрица, индексы, две колонки, таблицы с объединённой шапкой,
рисунок, колонтитулы.
13.10.2026: из 13 формул с латинскими обозначениями верно 13; текст, порядок двух
колонок, таблицы (35 ячеек из 35) и снятие колонтитулов — без потерь. Русские
индексы модель читает латиницей («V_обр» → «V_{op6}», «‰» → «%»), поэтому к такой
формуле приписывается её текст из PDF: `\text{[K п = V пор V обр · 100 %]}`
(`parse/orchestrator/formulas.py`, там же — снятие мусора после формулы). Номер формулы
модель не видит (рамка узкая), а текст на него ссылается («Combining (55)…»), поэтому
номер берётся из текста PDF и ставится в конце формулы: `\quad (55)`. Не `\tag{55}`:
просмотрщик без его поддержки показывает буквы «tag» — похоже на тангенс.
Цена: на процессоре около 2,3 с на формулу; на видеокарте формулы идут пачками по 32
(у docling — по 5): статья на 31 страницу с 67 формулами — 53 с вместо 186 с
(14.10.2026, RTX 5070 Ti; без формул та же статья — 13 с).

Модели формул в docling нет (он сменил устройство) — добыча и разбор не начинаются:
раньше разбор шёл в отдельном процессе с одним предупреждением, и формулы молча
портились. Выключить формулы — ключ `--no-formulas` (`add`, `all`, разбор папки PDF).

**Формулы в базе** (`georag/index/formulas.py`, перенесено из AgentKB). При загрузке
(`ingest`) формулы статьи берутся из её разметки docling (`<doc_id>.docling.json`):

- во фрагменте формула стоит между `$$…$$` — страница рисует её (KaTeX 0.16.11, копия
  в `web/static`, работает без интернета), в Телеграме она моноширинным, а кнопка
  «Формула (N)» под фрагментом присылает её картинкой (рисует matplotlib по LaTeX: PDF
  статей не хранятся);
- модель ответа по правилу 8 цитирует формулу дословно с номером и фрагментом — «по
  формуле (2) [3]: $$…$$» — и своих формул не выводит; формула отдельной строкой в
  ответе — не утверждение без ссылки, чистка ответа её не убирает;
- в вектор фрагмента вместо голого LaTeX идёт формула словами: номер, знаки
  («ρ = ρ_0 (1 − φ)»), фраза перед ней и «где …» после — запрос по смыслу её находит;
- таблица `formulas` (номер, LaTeX, текст из PDF, страница, рамка, абзацы до и после,
  фрагмент, описание и его вектор) и `formula_refs` — какие фрагменты на неё ссылаются
  («из формулы (55)», «уравнение 3», «(2)»; голое «(2)» бывает и номером пункта — такая
  ссылка может быть ложной). Команда: `python georag.py formula <doc_id> [N]`,
  `formula --find "…"` — формулы по смыслу.

Статья с формулами, которых в таблице ещё нет, при следующем `ingest` загружается заново
(факты графа остаются: пометка `$$` — не изменение текста). Но у 43 статей, разобранных
до 13.10.2026, формул в разметке нет — только место, где они были: им нужен повторный
разбор PDF (скачать заново: PDF не хранятся).

**Рисунки** (`--figures`, `georag/chunks/figures.py`). Подписи рисунков — часть текста
и в базе есть всегда (проверено: подписи всех 1006 крупных рисунков базы — во
фрагментах). С `--figures` docling ещё и вырезает рисунки (`generate_picture_images`,
масштаб 2 — мелкие подписи на карте читаются), и модель со зрением (отдельный сервер:
у основной Qwen3-14B зрения нет, см. `КОМАНДЫ.md`, «Рисунки») описывает каждый крупный: тип, район и объекты, легенду, читаемые
названия и числа. Получается фрагмент «Рисунок (с. N). <подпись> Что на рисунке
(описание модели по изображению): …» — номер после текстовых фрагментов статьи,
страница рисунка. Мелкое (меньше 300 точек по короткой стороне) и рисунок без подписи
на первой странице (обложка, логотип журнала) пропускаются; рисунок, на который
модель не ответила, — тоже, статья от этого не теряется. Описывать приходится сразу:
PDF не хранится, а картинки из `docling.json` перед записью убираются (с ними
файл статьи весит мегабайты: 4,3 МБ против 205 КБ).

Проба 11.10.2026 на 8 рисунках двух статей (карты, схема алгоритма, графики): по 1–2 с
на рисунок; описания по существу верны, в двух — по одной ошибке (перепутаны условные
знаки; «синий — выше» без основания). Польза — то, чего нет в подписи: со схемы
алгоритма прочитаны CatBoost, LightGBM, SHAP, с карты — «Новый Уренгой» и
координаты рамки. Описание помечено как сделанное моделью, чтобы его не принимали за
текст статьи.

`index.jsonl` — журнал добытого. По нему работает дедупликация: ночной прогон по той же
теме не тащит те же статьи заново. `--force` игнорирует индекс.

Ссылок хранится две: на страницу статьи — для человека, и на PDF — чтобы цитата могла
указывать на страницу видом `pdf_url#page=7`.

Статусы, с которыми статья попадает в отчёт: `acquired` (разобрана), `no_fulltext`
(нашлась, но открытого PDF нет — осталась только ссылка), `fetch_failed`,
`parse_failed`, `rejected` (мимо темы), `unreviewed` (решение не принято — бывает
только с флагом `--no-fallback`, иначе за молчащую модель решает эвристика).
Одна плохая статья прогон не рушит.

## Темы и запросы

Тема идёт в вашу модель, модель возвращает поисковые запросы, по ним идёт поиск.
Этот шаг можно посмотреть и поправить, а не только доверять.

```
python -m georag.acquire.cli --queries-only
```

Пишете темы по одной с клавиатуры, модель отвечает запросами — по-русски и по-английски,
потому что источники двуязычные и англоязычные формулировки находят другие работы.
Тема может быть и свободной: не «рудные узлы», а «прогноз золотого оруденения на
Анабарском щите по космоснимкам» — модель сама разберёт её на аспекты.

```
python -m georag.acquire.cli --topics config/topics.yaml --queries-only --save-queries queries.yaml
python -m georag.acquire.cli --topics config/topics.yaml --queries-file queries.yaml
```

Первая команда сохраняет запросы в файл, который можно править руками. Вторая ищет
по этому файлу, уже не обращаясь к модели: думали один раз, ищем каждую ночь одинаково.
Это ещё и делает ночной прогон независимым от того, поднята ли модель.

Если готовых запросов для темы нет, модель спрашивается как обычно. Если она недоступна,
запросы составит эвристика: тема как есть плюс перевод по глоссарию предметной области —
«выделение рудных узлов» станет `delineation ore cluster`. Смешанных запросов вроде
«prospectivity gold анабарском» она не выдаёт: непереведённые слова отбрасываются,
а если переводить нечего, англоязычный вариант просто не появляется.

## Полная автоматика

Участие человека — только в списке тем. Дальше база пополняется сама.

```
python georag.py schedule
```

Один раз — и в планировщике Windows появляется ночная задача (это windows-аналог cron
из части 11 плана). Каждую ночь она запускает `python georag.py nightly`: добыча по всем
темам из `config/topics.yaml`, загрузка в базу, граф связей (до 1000 новых фрагментов за
ночь) и выписки по частым предметам для чат-бота (не дольше часа, см. «Сбор по
предмету»), лог прогона — в `.local\logs\`.
Проверить, не дожидаясь ночи: `python georag.py nightly`. Убрать: `python georag.py unschedule`.

`config/topics.yaml` — единственный файл, который вы правите. В нём уже лежат темы по вашему
проекту: выделение и прогноз рудных узлов, линеаментный анализ, дистанционное
зондирование, Анабарский щит, плюс англоязычные формулировки.

Чтобы прогон не требовал человека, закрыты три места, где он раньше был нужен:

**Модель может быть не поднята.** Раньше при недоступной модели все статьи получали
статус «нужно решение» и ждали человека — то есть ночной прогон был бесполезен.
Теперь отбор в этом случае делает детерминированная эвристика: считает долю терминов
темы в названии и аннотации, с той же обработкой русской морфологии, что в валидации.
Плюс небольшой глоссарий предметной области, чтобы по русской теме искались и
англоязычные работы, когда переводить некому. В отчёте по каждой статье видно, кто
принял решение — модель или эвристика. Ночной прогон сам поднимает модель и, если
её нет, переключается на эвристику вместо того, чтобы падать.

**Один адрес полного текста может быть заблокирован.** Теперь у статьи собираются все
известные копии — лучшая открытая, версия издателя, копии в репозиториях, — и они
пробуются по очереди, пока одна не отдаст настоящий PDF. Именно так лечится
Cloudflare у MDPI: издатель отдал проверку, а копия в репозитории отдала файл.
В записи остаётся список того, что пробовали.

**Прогон должен заканчиваться.** Кандидаты сортируются так, чтобы лимит уходил на
статьи, у которых есть полный текст, а не на те, от которых останется одна ссылка;
внутри — сначала свежие. Отбор ограничен сверху (`max_candidates`): двенадцать тем
по пять запросов дают сотни кандидатов, и без предела модель разбирала бы их всю ночь.

Чего автоматика не сделает в принципе: статью за платным доступом. Такая попадёт в
отчёт со статусом «нет открытого PDF» и ссылкой — решать, нужна ли она, придётся вам,
но это уже не блокирует остальные.

## Каталог источников

`config/sources.yaml` — единственное место, где добавляются источники. Python править не нужно
ни в одном из трёх случаев:

Если у источника уже есть готовый провайдер (`openalex`, `crossref`) — копируете запись
и меняете параметры. Искать только у Springer: `provider: crossref` с `member: 297`.

Если у источника свой JSON API — `provider: json_api`. В записи описывается, куда
обращаться и где в ответе лежат поля: `title`, `externalIds.DOI`, `authors[].name`,
`oa.url|link.url` (первый непустой из двух путей). Если в адресе есть `{query}`, запрос
подставляется в путь, а не в параметры. Готовый шаблон лежит в каталоге записью
`example_json_api` — скопировать, подставить имена полей из документации API,
поставить `enabled: true`.

Модуль в `acquire/providers/` нужен только для источника, который отдаёт не JSON —
XML, Atom, HTML. Всё остальное описывается в каталоге.

Способ доступа задаётся полем `mode`, и разница принципиальная. `api` — официальный
интерфейс, только такие опрашиваются автоматически; сейчас включены три: **OpenAlex**
(250+ млн работ, собирает копии по репозиториям, поэтому полных текстов находит больше
всех), **Crossref** (вся периодика с DOI без фильтра по издателю) и **MDPI** (тот же
Crossref с `member: 1968` — чтобы работы издателя гарантированно попадали в выборку).
`html` — документ забирается по прямой ссылке, поиска по сайту нет: так помечена
КиберЛенинка, у неё поиск закрыт в robots.txt. `manual` — нужен человек: Lens с капчей
и eLibrary с институциональным логином. В автоматику последние две категории не идут.

Дубли между источниками схлопываются по DOI, поэтому три источника не создают тройной
работы — только шире охват.

## Что учтено в добыче

**Аннотации OpenAlex приходят инвертированным индексом** — не текстом, а словарём
`{"слово": [позиции]}`. Если собрать их обратно неправильно, LLM фильтрует статьи
вслепую по пустым аннотациям. Сборка — в `providers/openalex.py`.

**Аннотации Crossref приходят фрагментом JATS XML** (`<jats:p>…</jats:p>`) — теги
снимаются, иначе модель фильтрует статьи по разметке. Это та же ловушка, что с
инвертированным индексом, только у другого источника.

**`pdf_url` часто отдаёт не PDF, а страницу статьи.** Поэтому проверяется сигнатура
файла (`%PDF-`), а не заголовок Content-Type, который у таких страниц бывает любым.
У MDPI к этому добавляется Cloudflare: он иногда отдаёт скриптам проверку вместо
файла. Такая статья получит статус `fetch_failed` с понятной причиной и ссылкой —
скачать её руками через браузер занимает полминуты, а в базу мусор не попадёт.

**Qwen3 — думающая модель.** По умолчанию она выдаёт блок `<think>…</think>`, который
ломает разбор JSON. Размышления выключаются (`think: false` плюс подсказка `/no_think`),
а на случай, если пробились, — срезаются из ответа; JSON вытаскивается по границам
скобок, а не прямым `json.loads`.

**Файл читается потоком с лимитом размера** — один геологический атлас на несколько
сотен мегабайт иначе съест память ночного прогона.

**Режим `--no-llm`** прогоняет ту же обвязку без модели: тема идёт одним запросом,
всё найденное принимается. Полезно, чтобы отделить проблемы поиска от проблем модели.

На выходе в `.local/parsed/`: `<имя>.md` (текст), `<имя>.json` (структура + отчёт валидации),
`<имя>.docling.json` (документ docling — чтобы перечанковать без повторного парсинга),
`<имя>.chunks.json` (чанки), `report-<run>.json` (сводка). Пошаговый лог — в `.local/logs/parse-<run>.jsonl`.

## Что поправлено по сравнению с типовым кодом

Всё ниже проверено на установленном docling 2.126.0, а не взято из статей.

**1. Распознавание картинок (OCR) выключено.** У docling оно включено по умолчанию
(`do_ocr=True`), а русского нет ни в одном движке по умолчанию (`EasyOcrOptions().lang` —
`['fr', 'de', 'es', 'en']`): русский текст распознаётся мусором молча. Нам OCR не нужен:
сканы останавливает зонд до разбора, а на PDF с текстовым слоем текст с OCR и без — тот
же (замер 13.10.2026), OCR только добавлял время. Поэтому `do_ocr=False` явно — и у
запасного PyMuPDF4LLM тоже (`use_ocr=OCRMode.NEVER`): он сам распознаёт страницы с
картинками, на статье в 31 страницу это 11 с вместо 6. Движок OCR не нужен и в
зависимостях: docling разбирает статью и при запрещённом импорте `easyocr` (14.10.2026),
поэтому в requirements просто `docling`, без `[easyocr]`.

**2. Токенайзер должен быть от модели эмбеддинга.** В официальном примере docling стоит
`sentence-transformers/all-MiniLM-L6-v2`, и его копируют как есть. Для BGE-M3 это неверно:
у XLM-R другой словарь, и на русском счёт токенов расходится в разы — чанки получаются либо
вдвое короче нужного, либо не влезают в лимит модели. Здесь токенайзер берётся из
`settings.embed_model_id = "BAAI/bge-m3"`.

**3. У HybridChunker нет перекрытия.** Проверено по полям установленного класса:
`always_emit_headings, delim, merge_peers, omit_header_on_overflow, repeat_table_header,
serializer_provider, tokenizer` — никакого overlap. В плане было «512 токенов, перекрытие 15%»;
нативно это недостижимо, чанкер режет по семантическим границам и компенсирует контекст
заголовками. Перекрытие и не добавляется: контекст вокруг найденного фрагмента добирается
при поиске — соседними фрагментами (`chat/search.py`).

**4. Эмбеддим одно, цитируем другое.** `chunker.contextualize(chunk)` возвращает текст с
заголовками разделов сверху — он идёт в модель эмбеддинга. `chunk.text` — оригинал, он идёт
в цитату. В базе лежат оба, как и написано в плане.

**5. Номера страниц.** Без них не выполнить требование «всегда указывай источник и страницу».
Они достаются из провенанса: `chunk.meta.doc_items[].prov[].page_no`. В туториалах этот уровень
метаданных обычно просто теряется.

**6. Статус конверсии разбирается, а не глотается.** `convert(..., raises_on_error=False)` плюс
явная проверка `ConversionStatus`: `PARTIAL_SUCCESS` — это не успех, а повод показать ошибки
и отправить документ дальше по цепочке.

**7. Зависания лечатся процессом, а не таймаутом.** `document_timeout` внутри docling
существует, но на залипании в нативном парсере не срабатывает — известны случаи, когда не
помогает и Ctrl+C. Для ночного cron это остановка всей очереди. Поэтому документы считает
отдельный процесс (`parse/parsers/worker.py`): он держит модели в памяти между файлами, а родитель ждёт результат и
убивает его при превышении лимита. Смерть процесса (OOM, сегфолт, отсутствующая зависимость)
распознаётся сразу, без ожидания полного таймаута.

**Ни один сбой не проходит молча.** У каждого в ошибке документа (журнал JSONL) — причина
и место, в консоли — первая строка:

| Что случилось | Что в ошибке |
|---|---|
| исключение в разборе | тип, сообщение, место (`файл.py:строка функция ← …`) и полный стек |
| процесс упал в нативном коде | код выхода словами («нарушение доступа к памяти (код 0xC0000005)») и стек, который процесс записал сам (`faulthandler`) в `docling-*.log` в папке журналов |
| процесс завис | «не ответил за N с» и стек «где висел»: процесс пишет его на 90 % таймаута, до того как его убьют |
| процесс не запустился | «docling не загрузился: …» — отдельно от падения на документе: родитель ждёт сигнала «готов» |
| результат не передаётся между процессами | сразу, а не через весь таймаут: результат сериализуется в самом процессе |
| сбой в самом конвейере (зонд, эталон, запись файлов) | документ — статус `failed`, в журнале шаг «сбой» со стеком; очередь идёт дальше |
| сбой или ноль фрагментов при нарезке | «нарезка: …» в отчёте документа — он не попадёт в поиск |

На Windows у процесса разбора отключено окно «Программа не работает»: иначе упавший
процесс ждал бы его закрытия, и ночной прогон писал бы «завис» через 900 с вместо «упал»
сразу. Файлы стеков без записей удаляются, со стеком — остаются для разбора. В добыче
сбой на одной статье даёт запись `parse_failed` с причиной («сбой: …»), а прогон идёт дальше.

**8. TableFormer.** `TableFormerMode.ACCURATE` — уже дефолт в 2.126 (старые статьи пишут, что
дефолт FAST). Оставлен ACCURATE: на геологических таблицах со сложными шапками это правильный
выбор, но режим вынесен в настройки, если понадобится скорость.

## Валидация

Без эталона работают эвристики — они ловят два самых частых провала:

- `has_text` — сколько символов на страницу. Мало — парсер почти ничего не вытащил
  (скан сюда не доходит: его останавливает зонд).
- `encoding_sane` — доля мусорных символов: `(cid:NN)`, знак замены, символы личного
  пользования, управляющие, значки, русский текст в чужой кодировке («Ð»Ð¸Ð½…»).
  Буквы и цифры любого письма — китайского, японского, тайского, грузинского — не мусор.
- `no_stray_cjk` — иероглифы внутри латинских слов («e紅白quake», «My町田1低»): битый
  шрифт в статье на латинице, доля мусора его не видит. Порог — `max_stray_cjk`, 1 % слов.
  Текст на китайском и японском (иероглифов больше десятой доли букв) не проверяется:
  латинский термин слитно с иероглифами там норма.

Не прошёл любую из них — документ разбирает запасной парсер.
- `no_pathological_repeats`, `pages_covered` — некритичные сигналы о поломке и о страницах,
  с которых ничего не извлеклось.

С эталоном (`<имя>.json` в папке эталонов, ключ `--golden` у разбора) добавляется сверка разделов,
ключевых сущностей, числа таблиц и страниц. Сущности ищутся с поправкой на русскую морфологию:
эталонное «Анабарский щит» находится в «в пределах Анабарского щита», «зона окварцевания» —
в «выделены зоны окварцевания», а «рудный узел» — в «рудного узла», где выпадает беглая гласная.
Последнее всплыло как раз на реальных эталонах: без обработки беглой гласной главный термин темы
не находился ни в одной статье. Одиночные термины требуют более длинной основы, чем слова внутри
словосочетаний, — иначе короткий корень начинает совпадать с чем попало.

Структурных заголовков в русской геологической периодике почти нет (из восьми проверенных
статей «Введение — Методы — Результаты — Заключение» нашлось в одной), поэтому сверка
опирается на сущности. Текстовый слой статей местами сам получен OCR («УДК» → «ХДК»),
поэтому сущности сверяются по основам слов, а не точным совпадением.

Доля пройденных проверок и есть метрика «точность парсинга» из части 15 плана — она считается
по каждому документу и попадает в сводный отчёт.

## Оркестратор: случаи

`georag/parse/orchestrator/`. Одно правило на все документы ошибается: дефис на конце
строки в одном PDF — перенос, в другом — настоящий; docling в одних PDF читает знаки
верно, в других — мусором. Поэтому каждая найденная проблема — отдельный случай: что за
проблема, что с ней делается, где она встретилась и на чём проверена. Оркестратор
проверяет случаи своего этапа и по каждому пишет в журнал, нашёлся он или нет и что
сделано (шаг «оркестратор», поле `cases`); найденные — в итог документа (`cases`) и в
карточку статьи при добыче. Сбой одной обработки не роняет остальные: у её случая —
«не вышло» с причиной, стек — в журнале, документ идёт дальше с тем, что было.

Процесс docling только конвертирует; вся доводка — у оркестратора, в основном процессе:
разметка docling загружается один раз, все случаи этапа «после разбора» правят её, и
Markdown, текст по страницам и разделы собираются заново.

Чего оркестратор пока не ловит: неверно распознанные формулы — модель docling путает
блок из нескольких формул друг под другом (статья FMM, (26)–(28)); сверка чисел формулы
с текстом PDF не годится — у docling этот текст в таких PDF сам испорчен. Запасной
PyMuPDF4LLM склеивает переносы на концах строк сам и вслепую, поэтому настоящий дефис на
конце строки у него пропадает. Математика внутри абзаца остаётся текстом (q1, R³), не
LaTeX.

## Зонд: вариант документа

`georag/parse/orchestrator/profile.py` (правила дефиса — `hyphens.py`). Документы разные, и одно правило на всех ошибается. Самое
наглядное — дефис в конце строки: в одних PDF это перенос внутри слова («госу-
дарственных» — склеить), в других — настоящий дефис («кварц- серицитовых»), а сам PDF
этого не говорит. Зонд до разбора, за доли секунды (PyMuPDF, первые 12 страниц, без
моделей) выбирает вариант, и по нему правятся дефисы в результате любого парсера:

| Вариант | Признак | Дефис на конце строки |
|---|---|---|
| скан | меньше 50 знаков текстового слоя на страницу | документ не разбирается, статус `scan` |
| переносы размечены | мягких переносов не меньше 5 | по мягкому — склеивается (`tidy`), простой — правила языка |
| с переносами | строк, кончающихся дефисом перед строчной, ≥ 1 % и ≥ 5 | правила языка |
| без переносов | таких строк почти нет | настоящий: «геолого-геофизический» |

Правила языка — без словаря: заглавная после дефиса или сокращение и символ элемента
перед ним — дефис настоящий; русское составное (первая часть от 5 букв на -о/-е, вторая
от 5 букв) — дефис; иначе русское склеивается. На ручной разметке 160 мест из базы
(13.10.2026): русских 74, верно 68, ошибки — составные с минералом («кварц-
серицитовые»). Латиница со строчной в обеих частях («hy- drothermal» / «ore- forming»)
без словаря не решается и не трогается.

Кто сделал PDF (Word, LaTeX), пишется в журнал, но решения не меняет: учебник из Word с
включёнными переносами кончает переносом 11 % строк. Минимум в 5 строк — от короткого
документа без переносов: в Google Docs три настоящих дефиса на концах строк
(«ИИ-/решений», «Стартап-/полигон») — уже 1,6 %.

## Цепочка попыток

```
зонд  →  скан: не разбирается, статус scan
   ↓ текстовый слой есть
docling  →  валидация  →  ok
   ↓ упал, завис или не прошёл
pymupdf4llm  →  валидация  →  ok
   ↓
статус manual_review + причина в отчёте

лучшая попытка  →  оркестратор: случаи после разбора  →  фрагменты
```

Если ни одна попытка не проходит валидацию, сохраняется лучшая из них (по доле пройденных
проверок) — чтобы было что смотреть руками, а не пустой файл. За 103 статьи базы
запасной парсер пробовался 4 раза и один раз спас статью, на которой docling упал.

## Текстовый слой: когда docling портит знаки (случай «испорченные знаки»)

`georag/parse/orchestrator/textlayer.py`. В части старых PDF docling читает математические шрифты без
таблицы Unicode мусором. Статья J. Comput. Phys. 1999 (Acrobat Distiller 3.0, TeX-шрифты):
«X 0 D .‰; fi; fl/» вместо «X0 = (ρ, α, β)», «4 : 2 ¢ 10 ¡ 4» вместо «4.2 · 10⁻⁴». Буквы
он при этом читает верно, а структура, таблицы и формулы (LaTeX от модели) хороши.
PyMuPDF те же знаки читает верно — поэтому всё остаётся от docling, а текст абзацев и
ячеек таблиц берётся из PyMuPDF по тем же рамкам на странице.

**Когда.** Если знаков (не букв) у docling заметно больше, чем у PyMuPDF на тех же первых
12 страницах. Калибровка 14.10.2026 на 10 PDF: статья FMM — 3,2 % лишних знаков; LaTeX,
Word, ABBYY, КиберЛенинка, презентация, книга — от 0 до 0,1 % (дефисы не в счёт: их docling
ставит по-своему). Порог — 1 %. Решение пишется в журнал всегда (шаг «оркестратор», случай «испорченные знаки»).

**Как.** Абзац заменяется, только если слова совпали с docling: те же слова от 3 букв,
без лишних — иначе остаётся текст docling. Рамки соседних строк у docling бывают
внахлёст, поэтому сначала пробуется узкая рамка, потом широкая, и берётся подходящий
кусок строк. Надстрочные знаки — символами «⁻⁴», «³». Дефис на конце строки — по
свидетельствам самого документа: слово стоит через дефис посреди строки — дефис; как
решил docling в этом абзаце; слово целиком есть в документе — склеить; иначе решают
правила варианта (зонд). Несколько знаков PyMuPDF тоже читает не тем (Φ как «8» в шрифте
MathTime, скобки в перекодированном CMEX10) — они правятся по имени шрифта; таблица
проверена только на этой статье.

На статье FMM: заменено 308 абзацев из 310 и 873 ячейки, 1,6 с; результат построчно
совпал с проверенным вручную разбором. Отдельно для всех документов: подпись рисунка
внизу страницы docling бывает принимает за колонтитул (FIG. 4 под векторным рисунком) —
такая подпись возвращается в текст (`orchestrator/captions.py`).

## Чистка текста после разбора

`georag/parse/orchestrator/words.py` — для любого парсера (docling, PyMuPDF), до того как
из текста собираются Markdown, страницы и фрагменты; у docling — и в ячейках таблиц.
Чинит то, из-за чего слово не находит поиск по словам:

- **мягкий перенос** (U+00AD). В части PDF (CyberLeninka и др.) им размечены все
  переносы, и слово оставалось разорванным: «ра¬ - бот», «рай¬ онов», «недоста¬ то¬ чно».
  Мягкий перенос всегда внутри слова — по нему слово склеивается вместе с пробелом и
  видимым дефисом. Обычный дефис в конце строки так не починить: «госу- дарственных»
  склеивать, а «рудно- магматических» — нет, без словаря не различить (в базе таких 108);
- **буквы-двойники**: латинская «p» в русском слове («веpxняя»), кириллическая «О» в
  формуле («TiО»). Буквы меньшинства, у которых есть двойник в алфавите слова,
  заменяются. Символ элемента перед словом («Moпорфировых» — Mo-порфировых) и буквы без
  двойника («Pbизотопного», «Feместорождение» — пропущенный пробел) не трогаются.

По базе (13.10.2026, 4272 фрагмента) чистка меняет 235 фрагментов в 21 статье: склеен
1031 мягкий перенос в 13 статьях, исправлено 26 слов в 11. Уже загруженные статьи она
сама не трогает — их можно поправить по разобранному тексту (PDF для этого не нужен):
та же функция к тексту фрагментов и новые векторы для изменившихся.

## Этап 2. База знаний: векторы, Postgres, гибридный поиск

Чанки, полученные на этапе добычи, превращаются в векторы BGE-M3 и ложатся
в PostgreSQL с расширением pgvector. Поиск идёт двумя способами сразу.

### Что ставится

```
docker compose up -d           # поднять базу (первый раз скачает образ ~400 МБ)
pip install -r requirements.txt
python -m georag.index.cli init
```

`init` создаёт таблицы и индексы. Команда идемпотентна: повторный запуск ничего
не сломает.

### Как наполняется и как ищется

```
python -m georag.index.cli ingest                       # добытое → векторы → база
python -m georag.index.cli stats                        # что уже лежит
python -m georag.index.cli search "рудные узлы Анабарского щита"
python -m georag.index.cli search "ore cluster" --year-from 2015 --limit 5
```

Повторный `ingest` не плодит дубли: документ с тем же числом чанков пропускается,
а при переиндексации его чанки обновляются на месте, по номеру. `--force` индексирует
заново. Граф при этом не теряется: у фрагмента остаётся прежний id, и факты ссылаются
на него по-прежнему; стираются только факты фрагментов, чей текст поменялся, — их
модель пройдёт заново при следующем `graph`. (Раньше чанки удалялись и вставлялись
заново, и `ingest --force` каскадом стирал весь граф.)

### Служебный текст журнала в базу не попадает

Ручная сверка 65 фрагментов с оригиналами PDF (`.local/logs/quality-20261005`) показала:
около 10 % фрагментов — не статья, а служебный текст журнала, и чат-бот на него
ссылался. Его убирает `georag/index/noise.py` — при каждом `ingest`, а для уже
загруженной базы — командой `python georag.py tidy`:

| Что | Как узнаётся |
|---|---|
| служебные разделы | по заголовку целиком: благодарности, финансирование, конфликт интересов, вклад авторов, «Publisher's note», сведения об авторах (раздел статьи «Machine Learning contributions» остаётся) |
| колонтитулы | кусок от 6 слов, который повторяется в ≥ 10 % фрагментов статьи и похож на шапку (ISSN, DOI, «№ 2/2026, с. 5-25», ©, www) или на название статьи; не длиннее 45 слов — повтор длиннее значит, что к шапке прилип текст, и он не трогается |
| мелочь в тексте | заглушки формул и рисунков Docling, адреса e-mail, фразы издательств («All claims expressed…», лицензия CC) |
| авторы и места работы | ≥ 3 упоминаний института, университета, кафедры… на каждые ~16 слов во фрагменте короче 150 слов |
| пустышки | после чистки меньше 4 слов, или меньше 12 и это не законченное предложение, или одни приметы журнала |

Повтор сам по себе не признак: в статье повторяются и названия районов, и столбцы
таблиц — это содержание. Подчищенному фрагменту `tidy` пересчитывает вектор; факты
графа у него остаются, если их цитата по-прежнему есть в тексте.

### Почему два поиска, а не один

* **Вектор** понимает смысл и переводит между языками: запрос «выделение рудных
  узлов» находит статью про *ore cluster delineation*. Но точные строки —
  «Анабарский щит», номер листа Q-49-XXI — он теряет.
* **Полнотекстовый поиск** Postgres наоборот: точные слова находит, смысл — нет.
  Русская конфигурация снимает окончания у кириллицы, латиницу отдаёт английскому
  стеммеру («clusters» — по «cluster»). Беглую гласную она не знает: «рудный узел»
  даёт основу «узел», «рудного узла» — «узл». Поэтому запрос собирается в коде:
  у такого слова оба варианта через «или». Так же с существительными на -ом, -ов,
  -ем, -ев: «разлом» стеммер режет до «разл», а «разлома» — до «разлом», и запрос
  «Персияновский разлом» не находил ни одного фрагмента; теперь к слову добавляется
  вариант «разлома».
* Полнотекст требует **все** слова запроса. Длинный вопрос словами целиком почти
  не находится — тогда второй, мягкий заход: хотя бы часть слов. Такое совпадение
  само по себе не доказательство и проходит, только если фрагмент ещё и близок
  по смыслу.
* Векторный индекс HNSW по умолчанию смотрит 40 соседей и больше 40 строк не
  вернёт — поиск выставляет `hnsw.ef_search` не меньше 100. С фильтром по году
  или источнику pgvector 0.8+ добирает строки после фильтра (`iterative_scan`).
* В модель эмбеддинга фрагмент идёт вместе с названием статьи и заголовками
  разделов — так кусок статьи про Анабарский щит «помнит», откуда он. После
  обновления до этой версии один раз: `python georag.py ingest --force`.

Результаты объединяются через **RRF** (Reciprocal Rank Fusion): складываются не
оценки, а места в списках, `score = Σ 1/(k + rank)`, k = 60. Оценки двух поисков
несопоставимы — косинус против `ts_rank`, — а места сопоставимы. В выдаче у каждого
попадания подписано, кто его нашёл: вектор, текст или оба.

### Где лежат данные

В docker-томе `georag-data`, а не в папке проекта: распаковка архива с кодом
и антивирус до них не дотянутся. `docker compose down` базу останавливает,
данные остаются; удаляет их только `docker compose down -v`.

Адрес базы по умолчанию — `postgresql://georag:georag@127.0.0.1:5433/georag`.
Другой задаётся переменной `GEORAG_DSN` или ключом `--dsn`.

## Этап 3. Граф знаний: факты из статей

Граф строит **Qwen3**: проходит каждый фрагмент и выписывает из него факты. Факт —
«от — связь — к» и предложение статьи, где он сказан (цитата). Предложения
фрагмента пронумерованы; модель называет номер, а цитату по номеру берёт код:

> «Билляхская зона» — **входит в** — «Анабарский щит»
> «оруденение» — **приурочено к** — «узлы пересечения разломов»

Модель пишет связь словами статьи, по-русски, 1–4 слова («приурочено к»,
«контролирует», «выявлено методом»), а имена — как их назвала статья: так факт
держится за предложение, и его можно проверить вопросами по цитате. Потом каждому
подтверждённому факту ставится тип: связь из закрытого списка и вид каждого конца
(минерал, порода, оруденение…) — см. «Типы связей». Граф и чат-бот берут тип; факт,
который не о геологии («Figure 2 — иллюстрирует — …»), в граф не идёт.

| Файл | Что делает |
|---|---|
| `config/graph-rules.txt` | правила для модели (правятся Блокнотом) |
| `config/synonyms.yaml` | словарь синонимов: разные написания одного и того же → одно имя |
| `georag/graph/facts.py` | проход модели по фрагментам и проверка каждого факта кодом |
| `georag/graph/store.py` | таблицы `facts` (факт с цитатой, фрагментом и статьёй) и `facts_pass` (какой фрагмент модель прошла, что отброшено и почему) |
| `georag/graph/synonyms.py` | чтение словаря; предложения синонимов (векторы + Qwen3) |
| `georag/graph/api.py` | граф из фактов: сеть для страницы, датасеты, отчёт, CSV |
| `georag/graph/kinds.py` | типы фактов: связь из списка и вид концов по цитате (ниже, «Типы связей») |
| `georag/graph/vectors.py` | векторы подтверждённых фактов (таблица `fact_vectors`) — для поиска по связям (ниже, «Поиск по связям») |

### Факты не пишутся самовольно

Модель — не источник истины: каждый её факт проверяет код, и не прошедшее в граф
не попадает.

| Проверка | Что отбрасывается |
|---|---|
| номер предложения | не число или такого предложения во фрагменте нет |
| концы в цитате | в предложении не видны «от» или «к» — с любыми окончаниями; в длинном имени (от трёх слов) может не хватать одного слова, но не имени собственного: «рудного района» не подтверждает «Онежский рудный район». Название может стоять предложением выше («This area…») — тогда цитата из обоих |
| не предмет | «от» или «к» — число или год; количество («385 ± 2 млн лет», «около 80 % сульфидов», «2 км»); ссылка на работу («Binotto (2015)», «Иванов и др., 2019», «работа [33]»); положение («южнее Персияновского разлома…»); общее имя без названия — одни общие слова («this study», «predictive model», «high positive values», «первый этап») |
| длина | имя длиннее 100 знаков или 8 слов |
| предлог | «в аномалиях Bi» — предлог снимается, факт остаётся |
| связь с самим собой | «от» и «к» — одно и то же |
| связь | пустая или длиннее 6 слов |

Упоминание ищется только целыми словами: «щит» не находится в «защиты», «магнетит» —
в «титаномагнетит». Короткие слова («зона», «руда») находятся в любом падеже.

Связь модель берёт из короткого списка в правилах («входит в», «приурочено к»,
«контролирует», «сопровождается», «связано с», «расположено в», «выявлено методом»…) —
так одна и та же связь не расползается на сотни написаний.

По ручной проверке 100 фактов добавлены «не предметы», которых не ловила и вторая
проверка моделью (Qwen3 поймала 5 ошибок из 24 и отбросила бы 10 верных фактов из
65 — поэтому её нет): местоимение («this event», «эти структуры»), человек
(«В. Н. Бобров»), год («1950s»), счёт без названия («three areas»), общее слово без
названия («месторождение», «study area»). Если в цитате предположение («вероятно»,
«считается», «probably», «косвенные признаки»), а в связи его нет — связь получает
пометку «предположительно». Готовый граф перепроверяется этими правилами без модели:
`python georag.py graph --recheck`.

### Подтверждение вопросами

Код проверяет, что слова факта есть в цитате, но не смысл: «пирит — содержит —
прожилки» проходит, хотя в предложении сказано другое. Поэтому каждый факт ещё
проверяется вопросами (`georag/graph/confirm.py`): модель отвечает по цитате, код
сверяет ответ с фактом. Четыре проверки — два вопроса и два пропуска, вперёд и назад:

    «Согласно предложению, „X“ — приурочено к — что именно?»   → должно быть Y
    «Согласно предложению, что именно — приурочено к — „Y“?»   → должно быть X
    «X приурочено к ___»  /  «___ приурочено к Y»

Все четыре — одним запросом к модели (раньше вопросы и пропуски шли двумя).

Число совпавших ответов (0–4) хранится в `facts.votes`; граф и чат-бот берут факты
с ≥ 3 (`store.MIN_VOTES`), остальные остаются в базе. На независимой выборке из 100
фактов с ручной разметкой: без проверки верных 73 %, с ≥ 3 подтверждениями — 89 %,
с 4 — 95 % (подробно — `.local/logs/quality-20261005`). Одним запросом на той же сотне
(2026-10-10, пересчитано на одной видеокарте, чтобы сравнение было честным): с ≥ 3 —
83 % верных при 81 % сохранённых верных, как и двумя запросами; с 4 — 92 % при
63 % (двумя — 92 % при 49 %). Прямой вопрос «верен ли факт?» этого не давал (Qwen3
ловила 5 ошибок из 24), граф по шагам и синтаксический разбор — тоже (50 % и 55 %
верных). Все факты фрагмента одним запросом — тоже нет: верных 77 % при 37 %
сохранённых.

Проверка идёт сразу при проходе `graph`: каждый факт подтверждается тем же
работником, который его выписал, и ложится в базу уже с голосами. Отдельно —
`python georag.py graph --confirm` (для фактов, оставшихся без проверки);
возобновляемая.

Так убираются выдуманные сущности («Выдуманный район», которого в тексте нет) и
названия, дописанные «по смыслу». Причины отказов копятся в `facts_pass` и видны в
`python georag.py graph --new`: по ним правятся правила.

Проход возобновляемый: прервать Ctrl+C — та же команда продолжит с того же
фрагмента. После правки правил — `graph --redo` (всё заново).

### Типы связей

`georag/graph/kinds.py`, `python georag.py graph --types` (идёт и после `graph`, и после
`graph --confirm`; `--redo` — заново у всех).

**Зачем.** Модель выписывает связь словами статьи, и на 7350 подтверждённых фактов
вышло 1693 разных связи, 1155 — по одному разу; самые частые — расплывчатые
(«содержит», «связано с», «сопровождается»). Среди 80 случайных фактов полезных — около
трети; остальное — «Figure 2 — иллюстрирует — …», «rock — содержит — quartz», «эталон —
расположен в — центральной части изучаемой площади», «Chlorite — отображено в — red»,
«золото — содержит — пирит» (наоборот). Такие факты попадали в датасет и оттуда — в
ответы: «золото содержится в аншлифах», «самородное золото характеризуется
гранулометрией».

**Почему не при выписывании.** Пробовали закрыть список связей прямо в правилах
модели (.local/logs/graph-v2-20261014, 40 фрагментов): модель перефразирует статью
(«associated with» → «локализовано в»), а проверка вопросами по цитате держится слов
предложения и такие факты отбрасывает — подтверждённых 12 вместо 79. Поэтому факт
выписывается и подтверждается по-старому, а тип ставится отдельным шагом.

**Как.** Модель видит факт с цитатой (по 10 за запрос) и отвечает: вид каждого конца
и связь из списка или «нет» (не о геологии: рисунок, цвет на карте, расчёт, свойство
вроде пробности). Код проверяет, что виды подходят к связи:

| связь | от | к |
|---|---|---|
| входит в | объект, структура, порода | объект, структура |
| сложено | объект, структура, порода | порода, минерал |
| локализовано в | всё, кроме метода | порода, структура, объект |
| контролируется | оруденение, объект, порода, минерал, элемент, процесс | структура, порода, процесс |
| содержит | порода, оруденение, объект, минерал, процесс, признак | минерал, элемент |
| ассоциирует с | минерал, элемент, оруденение | минерал, элемент |
| сопровождается | оруденение, объект, порода, структура, элемент, процесс, минерал | процесс, минерал, признак |
| генетически связано с | оруденение, объект, минерал, порода, элемент, процесс | процесс, порода |
| образовано при | всё, кроме метода и признака | процесс |
| указывает на | признак, минерал, процесс, структура, элемент, порода | оруденение, элемент, объект |
| выявлено методом | всё, кроме метода | метод |
| пересекает | структура, порода | структура, порода |
| сменяется | процесс, порода, оруденение, минерал | то же |
| относится к | объект, оруденение, порода, структура, минерал | то же |

Виды подходят только наоборот — факт разворачивается. Близкая, но не та связь
исправляется: «рудный узел включает оруденение» модель называет «входит в», а это
«оруденение локализовано в узле»; «порода содержит оруденение» — тоже «локализовано
в», наоборот. Объект без названия («рудный район», «study area») — обычно перепутан
вид: «bauxites», «basement rocks», «gold occurrences» модель зовёт объектом; вид
угадывается по словам имени (deposit, месторождение → оруденение; zone, разлом →
структура; rock, гранит, жила → порода), не угадался — факт не в граф. Стороны света и
положение («N, NW and southern regions», «between the SNNF and SNSF») — тоже.

«Входит в» — только в объект или структуру: по ней датасет собирает части целого, и с
«порода → порода» в датасет «гранитов» попадали мигматиты, сланцы и кварциты. Порода
в классе пород — «относится к».

**Что вышло** (14.10.2026, 7350 подтверждённых фактов, 25 минут модели): тип у 3768
(51 %); не в граф — «не о геологии» 2092, виды не подходят к связи 674, объект без
названия 386, «не предмет» 275, связь не из списка 135, сторона или положение 20. Из
оставшихся чаще всего: локализовано в — 1060, сопровождается — 472, содержит — 452,
сложено — 399, входит в — 351. На пробе из 150 фактов из оставленных верно около 80 %
(в старом графе — около трети). Факты без типа остаются в базе (`type_note` — почему);
порог можно поменять и поставить типы заново, не выписывая факты. Правила кода (имя —
не свойство и не проба: «аншлифах», «гранулометрией», «составом» в любом падеже) можно
перепроверить без модели — `kinds.recheck`.

Колонки типа добавляются к facts, только когда их ещё нет, и ждут блокировку не дольше
10 с: ALTER TABLE ждёт конца всех транзакций с facts и, пока ждёт, не пускает к ним
других — на работающем сервере чат-бот вставал бы (так и случилось при проверке:
запрос простоял 5 минут за транзакцией оценки).

**Где тип нужен.** Граф (`api.Graph`) берёт тип вместо слов статьи, у сущности — вид
(какой ей чаще ставили). Сводка датасета для модели — строкой на тип: «золото
ассоциирует с: алтаит (1 статья), висмутин…», «кварцевые жилы содержит: золото (2
статьи), антимонит…», «золото содержится в: кварцевые жилы…», от самой весомой; факты
без типа — как раньше, по одному. Отпечаток графа считает и типы: поставили — граф
собирается заново.

**Что изменилось в ответах** (14–15.10.2026, `.local/logs/graph-v2-20261014`; вместе с
правками ответа из раздела «Этап 4» — без обрывков, повторов, выдуманных переводов, со
вторым заходом при отказе). 12 вопросов о связях, сравнение вслепую с ответами до правок
(оценивала другая языковая модель, не геолог): лучше после — 6, до — 4, вровень — 2. Ушли «золото
содержится в аншлифах», «самородное золото характеризуется гранулометрией», списки фактов
графа вместо ответа. Проигрыши: поиск принёс статьи об углеводородах (разломы), в сводке
«гидротермальных изменений» остались английские имена вроде «Magnetic lows», а на
«кварцевые жилы» модель расписала каждый факт сводки отдельным пунктом (54 утверждения).
29 вопросов оценки: по ответу 24 из 29, как и до; обрывков разделов 18 → 0, повторов
строк 58 → 0, среднее время ответа 20,0 → 15,1 с (до правок один ответ зациклился).

### Скорость и рост базы

Почти всё время графа — это модель, пишущая ответ: прочитать фрагмент ей 0,3 с,
а написать ответ — 74 токена в секунду. Ускорять поэтому нужно не код, а то,
**сколько модель пишет** и **сколько пишет одновременно**. Замер на одних и тех же
120 случайных фрагментах, RTX 5070 Ti, `qwen3:14b` (2026-10-10):

| Что | Было | Стало |
|---|---|---|
| ответ модели | факт с переписанной цитатой; 72 % фактов код отбрасывал, две трети — из-за цитаты | номер предложения вместо цитаты: ответ вдвое короче |
| сколько запросов сразу | 1 | 4 (`--workers`; тогда — Ollama с `OLLAMA_NUM_PARALLEL`, теперь vLLM) |
| выписать факты, на фрагмент | 3,55 с | 0,80 с |
| подтверждение | два запроса на факт, после всего прохода | один запрос, сразу при проходе |
| всё вместе (выписать и подтвердить) | 519 с | 258 с |
| подтверждённых фактов | 65 | 153 |

Вся база (4272 фрагмента, копия базы, обычный `graph --redo`): 2 ч 44 мин и 7334
подтверждённых факта; прежним способом 05.10 — около 8 ч 10 мин (выписать 7 ч,
подтвердить 1 ч 10 мин) и 2182 факта. На подтверждённый факт — 1,3 с против 13,5 с.

Слепая ручная проверка подтверждённых фактов (по 45–60 из каждого варианта
вперемешку, без пометки, откуда факт): прежний способ — верно 60 %, неточно 11 %,
бесполезно 29 %; новый — 52 %, 15 %, 30 %, ошибок 3 %. Разница в пределах
погрешности (±13 %), а верных фактов вдвое больше: около 80 против 39.

Что пробовали и не взяли (подробности и цифры — `.local/logs/graph-speed-20261010`):

* **другой движок** — llama.cpp (`llama-server`) с теми же четырьмя слотами даёт то
  же, что Ollama (0,79–0,87 с на фрагмент), вторая программа не нужна;
* **угадывание продолжения по тексту запроса** (n-gram speculative decoding) —
  ускоряет переписывание цитат на 30 %, но цитат больше нет, а без них выигрыш 9 %;
* **новые модели** Qwen 3.5 (9B и 4B со встроенным ускорителем MTP) — пишут
  быстрее (до 180 токенов в секунду), но переводят названия на русский и подставляют
  заготовки из примера: подтверждённых фактов 30 и 33 против 153;
* **отбор фрагментов заранее** — пропускать те, где фактов не будет, по их векторам:
  даже идеальный отбор 40 % фрагментов экономит 17 % времени — модель и так быстро
  отвечает «фактов нет»; время уходит на фрагменты, где факты есть;
* **все факты фрагмента одним запросом на подтверждение** — точность падает (выше).

Как с этим у других: LazyGraphRAG (Microsoft) и FastGraphRAG не зовут модель при
загрузке вовсе — понятия выделяются разбором текста, связи — по совместной
встречаемости, граф шумнее; KET-RAG зовёт модель только на «главных» фрагментах.
Нам нужны связи с цитатами и проверкой, поэтому модель остаётся, но работает
вчетверо меньше на факт.

**Новые статьи граф не пересчитывают.** Модель проходит только фрагменты, которых
ещё не видела (`facts_pass`), и только новые факты подтверждает. Граф в памяти
(страница, чат-бот, датасеты) не собирается заново: `api.graph()` видит, что к
фактам только добавились новые (прежние не тронуты — их число и подтверждения
те же), и дописывает их к готовому графу (`Graph.extended`); прежний граф при этом
не меняется — его в этот момент читают другие запросы. Сборка с нуля — после
правки словаря синонимов, удаления или перепроверки фактов. Для масштаба: сборка
с нуля растёт линейно — 0,7 с на 2 тыс. фактов, 12 с на 90 тыс.; дописать статью
(40 фактов) к графу на 90 тыс. — 19 мс.

Подпись узла при дописывании не меняется — иначе старые связи и новые разошлись
бы по разным узлам. Поэтому она может отличаться от той, что выбрала бы сборка с
нуля (самое частое написание), — регистром: «Pegmatites» вместо «pegmatites».
Узлы и связи те же; подписи выравнивает следующая сборка с нуля (перезапуск
страницы или правка словаря).

### Словарь синонимов

Одно и то же статьи пишут по-разному: «Donetsk basin», «Донбасс», «Донецкого
бассейна». Падеж и число код сводит сам (`text.name_key`: основы слов, беглая
гласная, английское множественное), остальное — словарь `config/synonyms.yaml`:

```yaml
имена:
  Донецкий бассейн: [Donetsk basin, Донбасс, Donbass]
связи:
  приурочено к: [приурочен к, associated with, hosted by]
обратные:
  входит в: [включает, состоит из, contains]
```

«обратные» — та же связь в другую сторону: «щит включает зону» — это «зона входит в
щит». Такие факты разворачиваются при чтении; раньше «включает» (его в графе было больше,
чем «входит в») в датасеты «часть — целое» не попадало.

Ключ имени (`text.name_key`) сводит падеж и число: «разлом», «разлома», «разломы» —
одно; беглая гласная — только там, где она бывает (узел — узла, песок — песка), иначе
разное сливалось («соль» и «сель»).

В словаре — **только настоящие синонимы**: перевод, сокращение, другое написание.
Частное и общее («random forest» и «машинное обучение»), часть и целое — не
синонимы: это факты, их записывает модель. Чего в словаре нет, идёт в граф как
написала модель. Словарь применяется при чтении, а не при записи, поэтому его
правка действует сразу — модель заново проходить не нужно, страница и бот
перечитывают файл сами.

Пополнять словарь помогает модель, решает человек: `python georag.py synonyms`
находит похожие имена (векторы BGE-M3, похожесть от 0.8), Qwen3 по парам решает,
одно ли это, и предложения ложатся в `.local/synonyms-предложения.yaml` — в том
же виде, что словарь. Нужные строки переносятся в `synonyms.yaml` руками; сама
модель словарь не правит.

### Автосинонимы

`georag/graph/autosyn.py`. Модель пишет одно и то же чуть по-разному («Landsat8 OLI»
и «Landsat-8 OLI», «mineralised» и «mineralized», «рудопроявление Эльвенейское» и
«Эльвенейское рудопроявление»), ключ имени этого не сводит, а словарь — только то,
что в него внесли. Автосинонимы сводят такие написания сами.

Имя каждой сущности графа (самое частое написание ключа) превращается в вектор
BGE-M3 и хранится в таблице `entity_names` (ключ, написание, вектор, `canon` — чьё
это написание, похожесть) с индексом HNSW. Новое имя сравнивается не со всеми, а с
пятью ближайшими уже известными через индекс; первое с похожестью от 0,95, слить
с которым не мешают правила кода, — и новое становится его написанием (`canon`).
Так новые статьи **добавляются, ничего не пересчитывая**: считаются векторы только
новых имён, старые остаются. Всё заново (`graph --names --redo`) — после правки
порога или правил; тогда имена идут от самых частых, и узел подписывается самым
частым написанием. 9439 имён — около 80 с.

Правила кода (`guard`) не дают слить похожее, но разное: разные числа («образец
JCBN50» и «JCBN45»), стороны света и степени («Восточное» и «Западное рудное тело»,
«northeastern» и «northern», «высоким» и «низким значениям»), разные собственные
имена. Когда таких слов два и больше, сверяется и слово после каждого: «high
thorium and low uranium» и «high uranium and low thorium» — те же слова, но про
разное; одно такое слово в другом месте — то же самое («magnetic low zones» и «low
magnetic zones»).

Почему порог 0,95, и почему серая зона сама не сливается — ручная проверка 100 пар
соседних имён графа (11.10.2026): от 0,95 одно и то же в 22 парах из 25 (с
правилами — 22 из 23 слитых); 0,85–0,95 — в 28 из 50, а Qwen3, решая по таким
парам, ошибается в каждой третьей (верных 22 из 31). Переводы и сокращения
векторы тоже не ловят: у синонимов из словаря похожесть в среднем 0,70, у «WofE»
и его расшифровки — 0,28. Поэтому словарь остаётся, и он главнее: имя из словаря
автосинонимы не трогают (`autosyn.extend`). На всей базе — 74 слитых пары, ни
одной ошибочной при ручном просмотре, правила остановили 18.

Граф в памяти собирается заново, когда меняется таблица (её отпечаток — часть
отпечатка словаря). `graph` сводит новые имена сам, после подтверждения фактов.

**Векторы статей пересчитывать не нужно**, когда добавляются статьи или имена:
вектор зависит только от текста и модели векторов. Пересчёт — если сменилась
модель векторов, изменился текст фрагмента (новое разбиение на фрагменты) или
то, что идёт в вектор (например, название статьи к тексту). Сведение имён —
дело глобальное (новое имя может оказаться ближе к другому), поэтому новые имена
присоединяются к ближайшим известным, а полный пересчёт дешёвый и делается
изредка.

### Датасет — у любой сущности

Датасет — все факты о сущности: с чем и как она связана, в скольких статьях это
сказано, дословные цитаты и ссылки на статьи. Есть у каждой сущности графа — у
щита, у метода, у процесса. Особая связь одна — **«входит в»** (часть → целое):
датасет Анабарского щита включает и факты о том, что в него входит по фактам
«входит в», на любую глубину.

Готовых датасетов нет, и нигде они не хранятся: датасет собирается из фактов в
момент запроса. Модель прошла новые статьи — появились новые сущности со своими
датасетами, у старых прибавились факты; правка словаря синонимов тоже сразу
меняет датасеты. Числа в списке датасетов и в карточке одни и те же: строк-фактов
(«от — связь — к», сколько бы фрагментов за ней ни стояло) и статей за ними.

Имени собственного нет среди сущностей, но оно стоит внутри других — «зоне
Персияновского разлома», «дайки вдоль Персияновского разлома» — датасет «Персияновский
разлом» собирает факты всех таких сущностей. Только для имён собственных: у «золото»
таких «родственников» сотни, и они о другом.

Датасет показывает карточка узла на графе (с таблицей для Excel), отдаёт
Телеграм-бот (/dataset), по нему отвечает чат-бот на «что известно о …».
Адреса: `GET /api/datasets` (у кого больше всего фактов), `GET|POST /api/dataset`
(`name`, `format=csv`); команда `python georag.py dataset "Анабарский щит"`.

### Граф на странице

Граф (`/api/network`) — на своей вкладке «Граф связей», как в Obsidian. Узлы — сущности и
статьи; рёбра — факты со стрелкой по направлению связи (подпись связи видна у
выбранного узла) и тонкие линии «из статьи» — от статьи к сущностям, о которых она
говорит. Щелчок по сущности — её датасет: строки фактов, по нажатию — цитата и
кнопка статьи; щелчок по статье — о чём в ней факты и «Разбор статьи целиком».
Над графом — поиск узла (кнопка «Найти» и список найденного; по основам слов:
«персияновский разлом» находит «зоне Персияновского разлома»; если имя стоит внутри
нескольких узлов — строка «Все факты о …» со сводным датасетом) и фильтр «от 2 / 3 / 5
статей». Раскладка устойчива к узлам с сотнями связей: пружина делится между концами
по числу связей (как в d3-force), а «показать всё» не учитывает крайние 2 % узлов —
раньше одна статья с 239 связями улетала, и граф сжимался в невидимую точку.

### Граф в деле

**Связи под ответом.** Ответ чат-бота строит поиск по фрагментам, а граф — карта рядом
с ним: под ответом блок «Связи из графа» — связи, которые граф выписал из
процитированных фрагментов (`/api/facts?chunks=…`, `graph.api.facts_response`; у
источника для этого есть `chunk_id`). Щелчок по имени открывает его на вкладке графа —
со всеми связями по базе; по номеру [n] — сам фрагмент; цитата — при наведении. В
Телеграме то же — кнопка «Связи» под ответом: связи списком, имена кнопками, кнопка
— картинка связей сущности с переходом к соседям.

**Сколько граф даёт ответам** (13.10.2026, база с новым графом, 7350 подтверждённых
фактов; каждый вопрос задан дважды — с графом и без, `eval --no-graph`;
данные — `.local/logs/graph-ab-20261013`):

| вопросы | граф участвовал | прошли с графом | прошли без графа |
|---|---|---|---|
| вопросы оценки (29) | в 2 | 25 | 25 |
| вопросы из фактов графа (28) | в 5 | 5 | 6 |
| «что известно о X» (12) | в 9 | 12 | 12 |

В обычных вопросах граф почти не включается: модель при разборе не называет предмет,
и кандидатов из графа нет. Даже на вопросах, составленных из его же фактов, ответы без
графа не хуже: нужные статьи гибридный поиск находит сам (64 % против 57 % с графом,
в пределах разброса). В «что известно о X» граф собирает датасет, и статей в ответе
чуть больше (5,2 против 4,5), но вслепую ответы с графом лучше в 5 из 12, без графа — в
5, вровень — в 2 (оценивал не геолог). В трёх из этих вопросов граф вообще
не включался, а «без графа» всё равно выиграл все три — это и есть разброс самой
модели. Вывод: всё, что граф знает, лежит во фрагментах, и поиск по векторам и словам
до этого добирается сам; заметной пользы ответам граф не даёт. Граф полезен как
отдельный инструмент — карта связей и датасеты с цитатами, — но строить его ради
чат-бота не нужно.

**Вопросы о связях — по графу.** Исключение — вопросы о том, с чем связан предмет:
«с какими минералами связано золото», «с чем ассоциирует хлорит», «что сопровождает
оруденение», «где встречается арсенопирит». Поиск приносит 8 фрагментов, и связи в
ответе — только те, что в них попали; граф видит все связи сущности сразу, со счётом
статей. На 12 таких вопросах (путь через граф включён принудительно, против поиска без
графа; `.local/logs/graph-ab-20261013`, `relations_*`, `оценка-связи-вслепую.txt`) вслепую
ответ через граф лучше в 7, поиском — в 2, вровень — в 3; связей в ответе в среднем 16
против 5. Минус — в ответ попадает и мусор графа («аншлифы», «гранулометрия» среди
минералов золота). Модель такие вопросы «собрать всё» не отмечала (0 из 12), поэтому их
узнаёт код — по формулировке (`about_links`, `_RELATIONS` в `chat/plan.py`): теперь
по графу идут 11 из 12 (у «линеаментов» нет датасета — в графе они по-английски),
среди вопросов оценки — 4 из 29 вместо 3 (добавился вопрос тоже о связях). Так у
вопросов два пути: о связях сущности — граф, остальные — поиск по фрагментам.

**Поиск по связям — проверен и выключен.** Идея: держать связи в том же пространстве
векторов, что и фрагменты, и искать по тем и другим сразу. У каждого подтверждённого
факта (голосов ≥ 3; 7350 на 14.10.2026) свой вектор BGE-M3 по тексту «от — связь — к.
цитата» — таблица `fact_vectors` с индексом HNSW (`graph/vectors.py`); векторы
фрагментов не меняются. Поиск с `facts=True` (`index/search.py`) ищет и по ним: факт,
близкий к запросу (от 0,6, `FACT_MIN_SIMILARITY`), приводит фрагмент, из которого
выписан, — до двух мест сверх найденного (`FACT_SLOTS`), и среди кандидатов модели
эти места за ним сохраняются (`chat/retrieval.py`, `keep_facts`); найденное и так
помечается «+ связь». Сам поиск по фактам — 4 мс на запрос (31 → 35 мс). Векторы
новых и изменившихся фактов считаются после `graph` и `graph --confirm`, отдельно —
`graph --vectors` (`--redo` — всё заново; 7350 фактов — 46 с на видеокарте).

Как сливать — подобрано без модели, по тексту вопроса, первые 12 фрагментов
(`.local/logs/facts-ab-20261014/offline.json`):

| способ | 29 вопросов оценки: ключевого | 30 вопросов из графа: ключевого | нужных статей |
|---|---|---|---|
| без фактов | 0,90 | 0,73 | — |
| третий список, слить по местам (RRF) | 0,88 | 0,70 | +1 / −3 |
| то же, вес фактов 0,5 | 0,88 | 0,80 | +1 / −2 |
| факты только поднимают найденное | 0,88 | 0,73 | +1 / −3 |

Слить на равных — хуже: фрагменты, похожие на запрос через свои факты, вытесняли
нужные. Текст для вектора — «связь + цитата» (сравнивалось при слиянии по местам):
только цитата — лучше на вопросах из графа, но хуже на вопросах оценки; только
«от — связь — к» — не лучше нигде. Близость
лучшего факта у вопросов не по теме — до 0,46, у вопросов по базе — в середине 0,61.

С моделью (14.10.2026, каждый вопрос со связями и без; вопросы из графа — дважды,
чтобы увидеть разброс; `.local/logs/facts-ab-20261014`):

| набор | со связями | без |

| 30 вопросов из графа: прошли поиск (два прогона) | 19, 19 | 18, 18 |

На вопросах оценки — ни одного вопроса, прошедшего иначе. На вопросах из графа поиск
стабильно чуть лучше (на один вопрос из 30), а ответы — нет: два прогона одного
режима расходятся на 2–3 вопроса, столько же, сколько режимы между собой. Вслепую
ответ со связями выиграл там, где поиск по связям принёс фрагменты и ответ на них
сослался (граниты, мигматиты, аргиллизация); проиграл там, где новых фрагментов не
было, — это разброс самой модели (повторы разделов, мусор датасета). Заранее
условились: оставить, если на вопросах оценки не хуже, на вопросах из графа и о
связях лучше, а время — не больше чем на 1–2 с. Ответы лучше не стали, поэтому в
чат-боте поиск по связям **выключен** (`Settings.fact_search = False`). Включить —
`fact_search = True`; сравнить на вопросах — `python georag.py eval --facts`. Вопросы
из графа составлены из тех же фактов, и выигрыш на них в поиске завышен.

* **Синонимы в поиске.** Вкладка «Поиск» и /search в Телеграме ищут и другие написания
  из словаря: «золото Донбасса» — ещё и как «золото donetsk basin» (`synonym_variants`).
  Только в полнотексте: вектор переводит сам, а точное название — нет. Под выдачей
  видно, как ещё искалось.
* **Кандидаты из графа в чат-боте.** Вопрос о названном предмете (не «собрать всё») —
  фрагменты, из которых выписаны факты о нём, идут модели в кандидаты первыми, без
  порога близости (`graph_candidates`, до 6). Редкое название вектор находит плохо, а
  граф знает, где о нём сказано. Брать ли — решает модель.
* **Вопросы оценки из фактов** — `python georag.py questions` → `.local/eval-graph.yaml`.
  Факт даёт вопрос (Qwen3 переформулирует, ответа в вопросе нет), ключевое — второй конец
  факта, «статьи» — где он сказан. Факты — из разных статей по очереди. Оценка по ним:
  `python georag.py eval --questions .local/eval-graph.yaml`.
* **Пробелы → темы добычи** — `python georag.py gaps` → `.local/topics-graph.yaml`:
  названия из словаря, о которых в графе нет фактов, и сущности, всё о которых — из
  одной статьи. Поровну тех и других. Добыть: `python georag.py all --topics topics-graph.yaml`.

## Этап 4. Чат-бот

`georag/chat/` (что в каком файле — в дереве в начале). Вопрос → поиск вместе с моделью (подробно — ниже, «Поиск
с моделью») → до 8 отобранных фрагментов, ≤3 из статьи; к фрагменту, начатому или
оборванному посреди мысли, добавляется соседний кусок того же раздела (ниже — «Соседние
куски») → Qwen3 с правилом «только по
фрагментам, номер фрагмента после каждого утверждения; нет ответа — одна фраза
„В базе знаний нет ответа“». **Настроек у ответа нет:** объём и вид — как просит
человек в самом вопросе («подробно», «кратко», «списком»); не сказал — по
существу: вывод в 1–2 предложения и главное списком. Частичный ответ разрешён —
с одной фразой о том, чего во фрагментах нет. Окно модели — 12 тысяч токенов →
номера сверяются, считается доля утверждений со ссылкой. Первые слова ответа
придерживаются, пока не ясно, не отказ ли это. Модель ничего не отобрала или
отказалась — источники не отдаются, событие `general` с пометкой «в базе знаний
такой информации нет», и второй вызов модели отвечает из общих знаний (без
фрагментов, с запретом на ссылки); `done.mode` = «без базы».

**Соседние куски.** Фрагмент — кусок раздела, и мысль бывает начата в предыдущем куске,
а закончена в следующем; там же — оговорка, обоснование или то, к какому району это
относится. По базе (13.10.2026, 4272 фрагмента): 8 % фрагментов начинаются посреди фразы,
4 % — со ссылки назад («Однако…», «Таким образом…»), 21 % кончаются не на конце фразы.
Поэтому к найденному фрагменту при ответе добавляется соседний кусок того же раздела, под
тем же номером (`add_neighbors` в `chat/search.py`): начат с середины мысли — спереди конец
предыдущего куска (до 600 знаков, целыми предложениями); короткий — сзади продолжение (до
1200); оборван на полуслове или на двоеточии — сзади конец фразы из следующего (до 500).
Таблица в соседи не берётся — её строки вместо начала фразы только занимают окно; кусок,
который и так среди фрагментов, не повторяется. Так дополняется 23 % фрагментов, в среднем
+103 знака (раньше — только короткие: 6 %, +70).

Сравнение на одном и том же отборе для 25 вопросов оценки (прежнее правило и новое, ответы
по очереди; `.local/logs/соседи-ab`): прошло одинаково — 20 из 25, ссылок 96,8 и 96,7 %;
все фрагменты по-прежнему влезают в окно; задание длиннее на 74 токена, ответ — на 1–2 с.
Метрики оценки разницы не видят: они проверяют ключевые слова и ссылки, а не полноту. Видно
по самим ответам: из 32 дополненных фрагментов ответ ссылается на 19, и в 5 берёт сказанное
только в добавленном куске. Фрагмент «…рактерны благородные металлы» без начала фразы не
говорит, о каком районе речь, — ответ ссылался на него без района; с началом фразы — «в
дальневосточной Арктике…». Оборванное «…таких минералов, как гётит,» дописывается до конца
перечня.

Фразы без ссылки на фрагмент — слова модели, а не статей. Когда модель дописала,
код (`drop_uncited`) убирает их из ответа и присылает ответ целиком событием
`revised`; что убрано — показано под ответом. Подводки к спискам («используют
следующие методы:») и фразы о самих фрагментах («во фрагментах не сказано…»)
остаются. Обрывков не остаётся: убиралась первая, обобщающая фраза раздела, и раздел
начинался с «Например, …» или «Эти длины волн…» (на 29 вопросах оценки — 18 таких
разделов). Теперь связка в начале следующей фразы («Например,», «Также», «В
частности,») снимается, а фраза, на которую следующая ссылается («Эти…», «Таким
образом…»), остаётся. Повторы тоже уходят (`drop_repeats`): модель иногда зацикливается — ответ на t04
повторял два абзаца по 30 раз (18 846 знаков, 147 с). Поэтому поток ответа и
обрывается, как только законченная фраза от 60 знаков дословно повторила уже сказанную
(`is_looping`): ответ о хлорите — 21 разная фраза по 8 раз, 26 тысяч знаков и 147 с.
Уходит строка, дословно
повторяющая сказанное (ссылки и разметка не в счёт); длинная строка без единого нового
слова против уже сказанной (раздел, написанный ещё раз с парой выброшенных слов); фраза,
уже сказанная в другом пункте («Это также отмечено в составе жильных минералов [2]» —
шесть раз). Пункты по одному шаблону с разными словами («кварцевые жилы содержат
пирит», «… антимонит») остаются. Фраза не режется на сокращении: после точки — строчная
буква («120 млн. лет»), значит, фраза продолжается; строка из одних ссылок («[3]. [7].»)
убирается.

**Отказ при найденном.** Бывает, что модель-отборщик признала фрагменты подходящими, а
модель ответа с первых слов пишет «В базе знаний нет ответа»: на s01 с одним и тем же
набором из 6 фрагментов — 3 раза из 3, хотя ответ в них есть (плотность линеаментов
2–3,5 км/км² совпадает с месторождениями). Тогда — второй заход с напоминанием правила 6:
есть хоть часть ответа — ответь на неё и назови, чего нет (`INSIST`; в событии `done` —
`insisted`). Отказ и во второй раз — ответ без базы, как раньше. Отказ узнаётся и в
других словах: короткий ответ (до 240 знаков), начатый с «В базе знаний нет…» («…нет
информации о металлогении Анабарского щита»), — тоже отказ; длинный с такой первой
фразой — частичный ответ.

Английские названия и термины модель переводила сама и ошибалась: «транскurrentных
сдвиговых зон», «UDMA (Уральско-Днепровско-Алтайского массива)», «chalcopyrite
(ковеллит)». Правило 4: чего не знаешь по-русски точно — пиши как во фрагменте,
латиницей, без придуманных расшифровок в скобках. Ответ из общих знаний о конкретном
объекте, которого модель точно не знает, выдумывал (Анабарский щит «в Хакасии»,
Билляхская зона «в Среднем Приобье»): теперь о таком объекте модель говорит, что статей
о нём в базе нет, и перечисляет, что о нём искать в литературе. Проверять каждое утверждение моделью пробовали: Qwen3 признала
неподтверждённым 1 утверждение из 14 действительно неподтверждённых, — не годится.
Правило в инструкции модели («не переноси сказанное об одном объекте на другой, не
добавляй своих выводов») тоже пробовали: на тех же 19 вопросах доля подтверждённых
утверждений не выросла (73 % → 65 %, в пределах погрешности), — правило убрано.

**Статьи расходятся.** Когда две статьи отвечают на вопрос по-разному, модель
выбирала одну и молчала о другой: на 8 вопросах с нарочно противоречащими
фрагментами обе позиции не показала ни разу, и правило «покажи обе» в инструкции
этого не изменило. Поэтому перед ответом идёт сверка (`find_conflicts`): модель
одним вызовом коротко пишет, что отвечает на вопрос каждый фрагмент (с районом или
объектом); пары фрагментов из разных статей (до шести) сравниваются — числа кодом
(диапазоны пересекаются — одно и то же, модель не нужна), остальное моделью:
противоречат ли ответы — то есть говорят об одном и том же и вместе неверны.
Найдено — в задание модели идёт пометка с номерами и словами фрагментов: «возможно,
отвечают по-разному; проверь по фрагментам — если это разное об одном и том же,
приведи обе позиции и скажи, что источники расходятся, если о разном — так не
называй». Последнее слово за моделью ответа: она видит фрагменты целиком. Под
ответом — строка «Статьи отвечают по-разному» (страница, «Как искал» в Телеграме),
в событиях — поле `conflicts`.

Проверка 11.10.2026. Сверка: на 8 нарочных противоречиях найдено 6, в 8 согласных
случаях лишнего нет. Первый вариант спрашивал «одно или разное» и на настоящих
вопросах оценки помечал почти всё — 84 пары в 17 вопросах из 19: разные стороны
ответа модель считала разными ответами. Со строгим «противоречат» — 3–4 пары на
прогон, и из них настоящих расхождений около половины («густая растительность
скрывает спектр пород» и «растительность не искажает сигнал» — да; «критерии
прогноза» и «минеральная перспективность» — нет). Повторный вопрос модели («могут ли
оба быть верны?») не помогает: на тех же парах он отвечает наугад. Поэтому пометка
мягкая: с твёрдой («источники расходятся») модель ответа повторяла это в 4 ложных
случаях из 5, с мягкой — ни в одном; найденные настоящие расхождения она показала
в 5 из 6 (с твёрдой — в 6 из 6). Итог — из 8 нарочных противоречий в ответе 5,
ложных «расходятся» на вопросах оценки нет. Цена — около 4 с на ответ (медиана
4,4 с); выключить — `Settings.check_conflicts = False`.

Ответ идёт потоком: `POST /api/chat` отдаёт строки JSON — сначала найденные
фрагменты, потом куски текста, в конце какие фрагменты процитированы. Страница
рисует ответ по мере прихода; кнопка «Стоп» обрывает поток, и модель перестаёт
писать. Блок размышлений Qwen3 выключен (`think: false`, `/no_think`) и на
всякий случай срезается из текста.

Вопрос вдогонку («а по космоснимкам?») модель при разборе переписывает в
самостоятельный — с предметом из прошлого вопроса, — и ищется он. Если модель
молчит, к вопросу приклеивается прошлый, но только если он похож на продолжение
(начинается с «а», «и», «ещё» или ссылается на сказанное: «там», «его», «этот»), —
раньше клеилось к любому короткому, и «Как испечь хлеб?» искался вместе с
космоснимками. Модели передаются две последние пары вопрос–ответ; номера [n] из
прошлых ответов убираются (они вели на другие фрагменты), а ответ «без базы»
помечается как не из статей.

Сообщение модели должно влезть в окно вместе с ответом: если не влезает, сначала
укорачивается история, потом отбрасываются последние фрагменты (`fit_budget`).
Модели велено называть, к какому району или объекту относится утверждение, и не
выдавать частный случай за общее правило; если все фрагменты из одной статьи — об
этом сказано отдельно.

Вопрос не о геологии (по разбору модели), и в базе пусто — бот отвечает коротким
отказом, без ответа из общих знаний. Вернуть прежнее — `Settings.general_off_topic`.

### Поиск с моделью

Обычный поиск (векторы + слова) на сложном вопросе ошибается в обе стороны: не
находит нужное, если оно сказано другими словами, и приносит похожее по словам,
но не о том. Поэтому поиск для чат-бота ведёт модель (`retrieve`):

1. **Разбор** (`plan_question`). Qwen3 (JSON, без размышлений) делит составной
   вопрос на части, до трёх — «какие признаки у рудных узлов и какими методами их
   выделяют» — это две; на каждую часть — по 3 запроса, русские и английские,
   терминами предметной области. Отмечает предмет вопроса и «собрать всё». Простой
   вопрос — одна часть.
2. **Широкий набор.** По запросам каждой части и по самому вопросу — гибридный
   поиск, слияние по местам (RRF), до 16 кандидатов на простой вопрос и по 8 на
   часть составного (и на вопрос целиком) с **мягким порогом**
   (похожесть от 0.35 или все слова запроса): лучше показать модели лишнее, чем не
   показать нужное. Один запрос дважды не ищется. С `Settings.fact_search` — ещё до
   двух мест фрагментам, которые привели близкие факты графа (выключено, см. «Поиск
   по связям»).
   Запросы ищутся **одновременно**: векторы всех запросов считаются одним вызовом
   (`embedder.encode`), а каждый поиск идёт в своём потоке со своим соединением
   с базой (`search_all`, до 4 потоков; запасные соединения не закрываются —
   `db.sibling`, новое стоит около 30 мс). Запросы всех частей составного вопроса
   ищутся сразу, до первого чтения моделью. 12 запросов — 138 мс вместо 481
   (11.10.2026). Порядок кандидатов может чуть отличаться от поиска по одному:
   вектор, посчитанный в пачке, отличается в пятом знаке (fp16), — на ответ это
   не влияет.
3. **Модель отбирает** (`judge_fragments`). Qwen3 получает вопрос, части и
   кандидатов — номер, название статьи, год и первые 1000 знаков, пачками по 12 (хвост до
   четырёх — вместе с последней), —
   **всех** (раньше читала первые 24, и третьей части вопроса почти ничего не
   доставалось), — и
   отвечает JSON: `подходят` (номера, от самых полезных), `не_хватает` (каких
   сведений нет), `запросы` (до трёх новых, без уже сделанных). Кандидат, где
   только похожие слова, а речь о другом, — не берётся, как бы высоко его ни
   поставил поиск.
4. **Ищет ещё.** Есть новые запросы — новый набор, модель читает только новых
   кандидатов (и видит, что уже отобрано). Всего до трёх кругов; стоп — когда всего
   хватает, запросов нет или новое не находится. В первом круге пусто — модель всё
   равно видит вопрос и подбирает другие запросы, прежде чем бот скажет «в базе нет».
5. **Отбор для ответа** (`_select`). Из отобранного — до 8: у каждой части свои
   места (не меньше двух; при двух частях — по три, при трёх — по два), остальное —
   в порядке модели, не больше 3 из статьи (пока есть другие). Модели велено
   ответить на каждую часть отдельным разделом.
6. **Модель молчит** (сервер выключен, сбой, не JSON) — отбор по порогу 0.45,
   как у обычного поиска (`find_sources`), с пометкой `judged: false`; замолчала
   во втором круге — берётся отобранное в первом.

Новый круг — только если модель говорит, чего не хватает, и предлагает запросы,
которых ещё не было (и не их перестановки); круг, не добавивший ни одного фрагмента, —
последний. Цена — вызов модели на пачку кандидатов. Окно модели задаёт сервер
(vLLM `--max-model-len 12288`); `Settings.num_ctx` — то же число, чтобы задание
вместе с ответом в него помещалось. Числа — в начале `chat/retrieval.py` (`WIDE`, `LOOSE_SIMILARITY`,
`JUDGE_MAX`, `MAX_ROUNDS`).

**«Собрать всё» — через датасет, а не поиском.** Вопрос вида «что известно об
Анабарском щите», «перечисли всё про окварцевание» поиском не решается: поиск
принесёт восемь похожих кусков, а фактов о предмете в базе может быть из тридцати
статей. Если модель отметила такой вопрос (или, когда модель молчит, по словам «что
известно», «перечисли», «полный список»…) или вопрос — о связях предмета («с чем
связан», «с какими минералами ассоциирует», «что сопровождает»… — это код узнаёт
всегда, см. «Граф в деле»), предмет вопроса узнаётся среди
сущностей графа — через словарь синонимов, без падежей, или по самому тексту
вопроса (самое длинное найденное имя), — и ответ собирается из его датасета:
сначала — сбором по статьям (ниже, «Сбор по предмету»); предмета нет ни в одной
статье — из датасета графа: фрагмент [1] — сводка «Факты о …» (все факты о предмете и о том, что в него входит,
со счётом статей), [2]… — фрагменты, из которых взяты цитаты главных фактов,
дальше — отобранное моделью из поиска. Пока граф не построен — обычный поиск с
моделью.

**Сбор по предмету** (`chat/collect.py`). Сколько информации ответ вообще видит: хлорит
упомянут в 214 фрагментах 46 статей, пропилитизация — в 139 фрагментах 29 статей, а ответ
по 8 фрагментам опирался на 3–7 статей. Окно модели — 12 тысяч токенов, все статьи
целиком в него не войдут. Поэтому — как глобальный поиск GraphRAG и map-reduce, но по
самим статьям, а не по сводкам сообществ (граф для них слишком редкий: из 4886 сущностей
лишь 325 встречаются в двух статьях и больше):

0. Предмет вопроса — сущность графа или названное моделью при разборе; модель его почти
   не называет, а граф знает не всё по-русски («migmatites», но не «мигматиты»), поэтому
   в вопросе о связях предмет берётся и из текста — после глагола связи: «С какими
   породами связаны мигматиты?» → «мигматиты» (`dataset.subject_in`). Без этого сбор на
   таком вопросе не включался, ответ видел 4 статьи из 23.
1. Названия предмета: словарь синонимов, имена графа, близкие по вектору BGE-M3 и без
   общих слов («хлорит» — «chlorite» 0,84; «зона хлорита» 0,79 и «chloritization» 0,71 —
   нет), английское название от модели (русские «варианты» модель сочиняет — не берутся).
   Хранятся в `collect_aliases` — только если модель ответила: без английского названия
   статьи на английском не найдутся.
2. Все фрагменты, где он упомянут (полнотекст по названиям), — по статьям; статьи — по
   числу упоминаний, до 30, из каждой — 2 лучших фрагмента.
3. Выписка по статье — отдельный вызов модели, 8 одновременно: с чем предмет связан,
   вид (минерал, порода, процесс…), как связан, где, дословная цитата. Спросили о
   минералах (породах, процессах… — по словам вопроса) — выписка **прицельная**: «выпиши
   ВСЕ минералы, которые фрагменты связывают с хлоритом, каждый отдельным пунктом».
   Общее задание («что статья говорит о предмете») давало около 5 пунктов на статью: в
   прочитанных фрагментах опора была у 71–100 % названий эталона, в выписке — 29–61 %.
   Прицельное на тех же статьях: хлорит 0,26 → 0,57, самородное золото 0,28 → 0,51,
   кварцевые жилы 0,73 → 0,69, и быстрее (56 с на предмет против 92).
   Пункт отбрасывается, если его цитаты нет во фрагменте, если он о самом предмете
   («хлорит — ассоциирует с») и если рядом с цитатой (300 знаков до и после) предмет не
   упомянут — ни именем, ни основами слов («argillized» для «argillic alteration»): без
   этого модель выписывала соседей по статье («кварц можно картировать по тепловым
   ИК-данным» — для хлорита). Проверка вслепую 30 пунктов: до неё 18 верных, после —
   около 26; основы слов вернули пункты процессов, которые проверка по имени целиком
   отбрасывала на две трети («Propylitic, Mineral = Calcite»), ценой части точности
   (около трёх четвертей верных на смеси предметов). Ответ, оборванный на потолке
   длины, не теряется: берутся целые пункты до обрыва (у самородного золота так
   терялись 8 статей из 22, и они перечитывались при каждом вопросе).
   Выписка хранится (`collect_notes`, ключ — предмет, виды и версия задания
   `MAP_VERSION`): второй вопрос о том же предмете статей не перечитывает.
4. Сводка — кодом: что упомянуто в скольких статьях и в каких («Чаще всего: эпидот — 7
   [10][12]…; в двух статьях: …»); спросили о минералах — в ней только минералы.
   Выписка оставляет название на языке цитаты (epidote в английской статье, эпидот — в
   русской), поэтому написания сводятся ключом (`spelling_key`: латиницей, с правилами
   названий минералов — -ite = -ит, c перед e/i = ц, h = г = х — без двойных букв и
   конечных гласных): на парах «calcite — кальцит» сходится 29 из 35, среди 1269
   названий из выписок склеено 49 групп, все верно (гранат и гранит — разные). В
   сводке пункт называется русским написанием, если оно есть в статьях базы, иначе — как
   в цитате. Раньше эпидот считался в сводке двумя пунктами, а хвост повторял по-английски
   то, что ответ уже назвал по-русски.
   Модель отвечает по сводке и выпискам статей (каждая — заметкой со своим номером),
   поиск добавляет 3 фрагмента целиком.
5. Хвост «Ещё в статьях базы»: чего из сводки модель не назвала (ни одним написанием),
   по убыванию числа статей, с номерами статей — дописывает код (`rest_of_summary`); в
   терминале (`ask`) он печатается после ответа. Даже со сводкой из 30
   статей модель перечисляет 10–20 пунктов: сводка покрывала 0,46–0,61 эталона, ответ —
   0,20–0,46.

Время: первый вопрос о предмете — 70–150 с (чтение статей 60–90 с), повторный — 40–90
с; без сбора — около 35 с.

**Выписки заранее** (`python georag.py collect`, и каждую ночь после графа — не дольше

Как искалось, видно под ответом — на странице, в Телеграме («Как искал») и в
`ask`: части и сколько фрагментов у каждой, сколько кандидатов прочла модель,
круги, чего не хватало и какими запросами искала ещё, из какого датасета собран

`checked`, `judged`. Оценка (`eval`) ищет так же и один раз — для проверки поиска и
для ответа (`prepare` → `answer(prepared=…)`).

## Телеграм-бот

`georag/tg/bot.py`, `georag/tg/ui.py`. Второй вход в ту же базу, рядом со
страницей: вопрос — тот же чат-бот (`chat/answer.py`), поиск — тот же гибридный
поиск, датасеты — те же, с CSV. Bot API — обычный HTTP через requests, новых библиотек нет. Бот
сам забирает новые сообщения (long polling), поэтому компьютеру не нужен ни
открытый порт, ни внешний адрес. Ответ модели показывается по мере написания —
правкой одного сообщения раз в полторы секунды; длинный ответ делится на
сообщения до 4096 знаков. Разметка — HTML Телеграма; если он её не примет, ответ
уходит простым текстом.

Интерфейс — кнопками (`georag/tg/ui.py` — только оформление, без сети и базы;
`bot.py` — логика). Меню внизу экрана (reply keyboard) заменяет команды; под
сообщениями — inline-кнопки: фрагменты ответа, «Как искал», «Остановить», листание поиска, статей и фрагментов статьи, факты, настройки.

**Картинка связей** (`georag/tg/picture.py`) — вместо интерактивного графа страницы,
которого Телеграм не покажет. «Факты» → сущность → картинка PNG: сущность в центре,
вокруг — с чем она связана (стрелка — направление факта, подпись — связь из статьи),
то, что в неё входит, — на внутреннем кольце, их связи — на внешнем, в своём секторе.
До 12 соседей — самые подтверждённые по числу статей. Под картинкой — соседи кнопками
(переход меняет картинку в том же сообщении, `editMessageMedia`), «Цитаты» (факты
списком, с источниками), таблица для Excel, вопрос боту. Рисует Pillow, шрифт —
системный с кириллицей; не нарисовалось — факты списком, как раньше.
В нажатии (callback_data, до 64 байт) — только действие и номера: `f:3:2` —
фрагмент [2] ответа 3; сами ответы, выдачи и список датасетов хранятся в
разговоре у бота (последние 20). После перезапуска бота старые кнопки отвечают
всплывашкой «кнопка от старого сообщения». Ответ модели пишется в отдельном
потоке, а цикл опроса тем временем принимает нажатия — поэтому «Остановить»
срабатывает сразу: поток ответа закрывается, модель перестаёт писать. Пока бот
пишет, второй вопрос в том же чате не берётся. Настроек у бота нет: подробно или
кратко — человек пишет в вопросе; /stats — что в базе и готова ли модель.

Доступ — `.local/telegram_users.txt` (перечитывается на каждом сообщении): id по одному в
строке; строка `*` — бот открыт всем, без ограничений. Без `*` чужому бот отвечает его
id — не чаще раза в 10 минут. Модель пишет
ответы по одному (`MAX_PARALLEL`): остальные ждут в очереди и видят своё место. Разговоров
в памяти — до 300, старые забываются. Одна копия бота на компьютере: занимается
локальный порт, выведенный из номера бота; вторая копия не стартует. Один и тот же
update_id дважды не обрабатывается. Токен — `.local/telegram_token.txt` или
`GEORAG_TG_TOKEN`. `web --tg` запускает бота в том же процессе, что и страницу:
модель векторов загружена один раз.

## Этап 5. Оценка

`georag/evaluation.py`, вопросы — `config/eval-questions.yaml` (около тридцати:
по признакам, территориям и методам, плюс контрольные не по теме). Для каждого вопроса код, а не модель, проверяет:

* **поиск** — нашлись ли близкие фрагменты и есть ли в них ключевые слова
  вопроса; на контрольный вопрос — что не нашлось ничего;
* **ответ** — по базе ли он, когда должен, и «в базе нет», когда должен;
  не отписка в одну фразу (от 150 знаков); у скольких утверждений ссылка на
  фрагмент (порог 60 %); нет ли ссылок на несуществующие фрагменты; есть ли
  ключевые слова в самом ответе.

Ключевые слова сравниваются без падежей, а однословные имена собственные и термины —
ещё и без алфавита (`text.translit_key`): «Koldar», «Колдар» и «Кольдар», «alunite» и
«алюнит» дают один ключ (короткие, до 5 букв, так не сравниваются: «Якут» нашёлся бы в
«acute»; начало составного имени не засчитывается: «Кулар» — не «Куларо-Нерский»).
Вопросы из графа (`questions`) берут в ключ все написания сущности — из словаря
синонимов и автосинонимов графа, и имя без вида места («Isfahan Province» → «Isfahan»).
Пересчёт трёх прошлых прогонов по 40 вопросам (`.local/eval-graph-v3.yaml`): засчитано
23 → 26, 23 → 25, 23 → 28; каждое новое прохождение проверено по цитате — верное, ложных
нет.

Отчёт — `.local/logs/eval-<дата>.md` и `.json`; каждый прогон сравнивается с прошлым.
Раздел «Где базе не хватает статей» называет вопросы, по которым поиск находит
мало; добирать — темами `config/topics-check.yaml`. Без модели оценивается только
поиск (`eval --only-search`).

## Общие части кода

* `georag/llm.py` — один клиент модели на весь проект, протокол OpenAI
  (`/v1/chat/completions`): JSON-ответ, ответ потоком, проверка «жив ли сервер и та
  ли на нём модель», выключение размышлений Qwen3 (`enable_thinking: false`). Сервер —
  vLLM в Docker (сервис `llm` в `docker-compose.yml`); адрес — `GEORAG_LLM`, по
  умолчанию 127.0.0.1:8100 (на 8000 — веб-страница). Тот же протокол у llama.cpp и SGLang: сервер можно
  сменить, не трогая код.
* `georag/text.py` — русский текст: нормализация, основы слов с беглой гласной,
  шаблон фразы в любой форме, деление на предложения. Раньше это было в трёх
  местах тремя разными способами.
* `georag/common.py` — общие ключи командной строки (`--dsn`, `--device`,
  `--model`, `--llm-host`) для всех команд.
