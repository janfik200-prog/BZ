# ГеоRAG — все команды и настройки

Как поставить и запустить — в `ЗАПУСК.md` в корне проекта. Здесь справочник: короткие команды,
полные команды со всеми ключами и тонкие настройки.

Всё набирается в терминале, открытом в папке проекта. Короткие команды
начинаются с `python georag.py`, полные — с `.venv\Scripts\python -m …`:
ими пользуются, когда нужен ключ, которого нет у короткой.

---

## 1. Короткие команды

| Что делаем | Команда |
|---|---|
| Поднять базу | `python georag.py start` |
| Что работает | `python georag.py status` |
| Добыть по одной теме | `python georag.py add "выделение рудных узлов"` |
| Сохранить ключ OpenAlex (один раз, обязательно) | `python -c "open('.local/openalex_key.txt','w').write('КЛЮЧ')"` |
| Добыть по всем темам | `python georag.py all` |
| То же, и рисунки статей описывает модель со зрением | `python georag.py all --figures` |
| По темам из другого файла | `python georag.py all --topics topics-anabar.yaml` |
| Посмотреть, что не по теме | `python georag.py clean` |
| Убрать не по теме | `python georag.py clean --apply` |
| То же, и Qwen3 проверяет каждую статью по теме | `python georag.py clean "тема" --apply` |
| Загрузить в базу | `python georag.py ingest` |
| Убрать служебный текст из уже загруженной базы (благодарности, колонтитулы, e-mail) | `python georag.py tidy` |
| Поискать | `python georag.py search "рудные узлы"` |
| Спросить чат-бота | `python georag.py ask "как выделяют рудные узлы?"` |
| Подробно или кратко — словами в вопросе | `python georag.py ask "кратко: как выделяют рудные узлы?"` |
| Выписки по частым предметам заранее (идёт и ночью) | `python georag.py collect` |
| То же для 40 предметов / только список, без модели | `python georag.py collect --limit 40` / `collect --dry-run` |
| Датасеты — у чего больше всего фактов | `python georag.py dataset` |
| Датасет любой сущности, таблица для Excel | `python georag.py dataset "Анабарский щит"` |
| Оценить базу и чат-бота | `python georag.py eval` |
| Оценить только поиск (без модели) | `python georag.py eval --only-search` |
| Добрать статьи под вопросы оценки | `python georag.py all --topics topics-check.yaml` |
| Граф: Qwen3 выписывает факты из статей | `python georag.py graph` |
| Проба графа на 30 фрагментах | `python georag.py graph --limit 30` |
| Вопросы оценки из фактов графа | `python georag.py questions` → `eval --questions .local/eval-graph.yaml` |
| Где не хватает статей → темы добычи | `python georag.py gaps` → `all --topics topics-graph.yaml` |
| Граф заново (после правки правил) | `python georag.py graph --redo` |
| Что нашла модель и где ошибалась | `python georag.py graph --new` |
| Перепроверить готовый граф новыми правилами кода (без модели) | `python georag.py graph --recheck` |
| Подтвердить факты вопросами по цитате (идёт и само после `graph`) | `python georag.py graph --confirm` |
| Предложения в словарь синонимов | `python georag.py synonyms` |
| Свести написания одного и того же (идёт и само после `graph`) | `python georag.py graph --names` |
| Поиск, статьи, чат-бот и граф в браузере | `python georag.py web` |
| То же + Телеграм-бот | `python georag.py web --tg` |
| Только Телеграм-бот | `python georag.py tg` |
| Бот молчит — проверить токен, доступ, кто писал | `python georag.py tg --check` |
| Сервер без браузера (только адреса /api) | `python georag.py serve` |
| Что в базе | `python georag.py stats` |
| Ночной прогон каждую ночь | `python georag.py schedule` |
| Ночной прогон сейчас | `python georag.py nightly` |
| Убрать ночной прогон | `python georag.py unschedule` |
| Остановить базу | `python georag.py stop` |

Порядок всегда один: **добыть → почистить → загрузить → граф → искать и спрашивать.**

## 2. Добыча статей — все ключи

```
.venv\Scripts\python -m georag.acquire.cli "выделение рудных узлов" --max-docs 5 --device cuda --mailto ваш@адрес --model qwen3:14b
```

По всем темам сразу — вместо темы в кавычках `--topics config/topics.yaml`.

| Ключ | Зачем |
|---|---|
| `--topics config/topics.yaml` | взять список тем из файла вместо одной темы |
| `--max-docs 5` | сколько статей разбирать за тему |
| `--device cuda` | считать на видеокарте |
| `--mailto ...` | вежливый режим OpenAlex и Crossref: ответы стабильнее |
| `--model qwen3-14b` | какая модель отбирает статьи (имя на сервере vLLM) |
| `--no-llm` | не спрашивать модель, решать эвристикой (когда модель выключена) |
| `--dry-run` | только поиск и отбор, без разбора — быстрая проверка |
| `--force` | не пропускать статьи, которые уже видели |
| `--tables fast` | быстрый разбор таблиц вместо точного |
| `--figures` | рисунки статьи — в базу фрагментами «Рисунок»: подпись и описание моделью со зрением (`qwen3.5:9b`) |
| `--per-query 25` | сколько результатов брать из каждого источника |

Только запросы, без поиска — посмотреть, что модель придумала по теме:

```
.venv\Scripts\python -m georag.acquire.cli "рудные узлы" --queries-only
.venv\Scripts\python -m georag.acquire.cli --topics config/topics.yaml --queries-only --save-queries queries.yaml
```

Файл `queries.yaml` можно править руками, а потом искать по нему, не
спрашивая модель каждый раз:

```
.venv\Scripts\python -m georag.acquire.cli --topics config/topics.yaml --queries-file queries.yaml
```

### Формулы

Формулы в статьях распознаются сами (в LaTeX) — модель Docling CodeFormulaV2 скачивается
при первом разборе (0,64 ГБ). Как это проверено — в `УСТРОЙСТВО.md`. Без формул
(быстрее, формулы останутся картинками): `python georag.py all --no-formulas`.

На странице формулы нарисованы, в Телеграме под фрагментом — кнопки «Формула (N)»:
формула картинкой. Найти формулу:

| Что | Команда |
|---|---|
| Формулы статьи: LaTeX, словами, кто на них ссылается | `python georag.py formula <doc_id>` |
| Одна формула — с номером (2) | `python georag.py formula <doc_id> 2` |
| Формулы по смыслу | `python georag.py formula --find "как плотность зависит от пористости"` |

### Рисунки под ответом

Рисунки статьи с подписью вырезаются из PDF при разборе (`add`, `all`, импорт папки) —
по рамке, которую нашёл docling: файлы `.local\acquired\<doc_id>.figures\fig-001.jpg`…,
перечень (номер по подписи «Рис. 3» → 3, страница, подпись, размер) — в поле `figures`
записи статьи. Рисунки без подписи (логотип журнала, значок, обложка) и мельче 40 пт не
берутся. При загрузке в базу каждый рисунок связывается с фрагментом, где стоит его
подпись, и с фрагментами, которые на него ссылаются: «рис. 3», «на рисунке 2а»,
«(рис. 5, 6 и 7)», «Fig. 4», «figs. 2 and 3».

Под ответом чат-бота на странице — рисунки фрагментов, на которые ответ сослался (до 4):
картинка и «Рис. 3 к [2], с. 9. Подпись»; нажать — целиком. В Телеграме — те же рисунки
фото после ответа (до 3).

Статьи, разобранные раньше, рисунков не имеют — их вырезает команда (PDF нужны, разметка
`<doc_id>.docling.json` уже есть, заново ничего не разбирается):

| Что | Команда |
|---|---|
| Вырезать рисунки всех разобранных статей и записать в базу | `python georag.py figures --pdf "C:\статьи\pdf"` |
| Только этих статей | `python georag.py figures --pdf "C:\статьи\pdf" <doc_id> …` |
| Заново и уже вырезанные | `python georag.py figures --pdf "C:\статьи\pdf" --redo` |

PDF ищется по пути в записи статьи, а нет его — файл `<doc_id>.pdf` в папках `--pdf` (с
подпапками). Статьи, добытые из сети (`all`), PDF не хранят — их рисунки вырезаются только
при разборе.

### Описание рисунков моделью (`--figures`)

Подписи рисунков в базу попадают и без этого — они часть текста статьи. С
`--figures` модель со зрением ещё и смотрит на сам рисунок и пишет, что на нём:
тип (карта, разрез, график, схема), район и объекты, легенду, читаемые названия и
числа. Каждый крупный рисунок становится фрагментом «Рисунок (с. 9). Рис. 8. … Что
на рисунке (описание модели по изображению): …» — его находит поиск и цитирует
чат-бот. Значки, логотипы и обложка пропускаются.

Нужна модель со зрением — у основной Qwen3-14B его нет. Это отдельный сервер vLLM,
например с `Qwen/Qwen3-VL-8B-Instruct-FP8` (около 11 ГБ скачивания). На 16 ГБ две
модели сразу не помещаются, поэтому на время добычи с рисунками основную
останавливают:

```
docker stop georag-llm
docker run -d --name georag-vision --gpus all -p 127.0.0.1:8001:8000 -v georag_georag-models:/root/.cache/huggingface vllm/vllm-openai:v0.30.0 Qwen/Qwen3-VL-8B-Instruct-FP8 --served-model-name qwen3-vl --max-model-len 8192
$env:GEORAG_FIGURE_LLM = "http://localhost:8001"     # в cmd: set GEORAG_FIGURE_LLM=http://localhost:8001
python georag.py all --figures --no-llm
docker rm -f georag-vision
docker start georag-llm
```

Проба 11.10.2026 (тогда — qwen3.5:9b): рисунок — 1–2 с. PDF не хранится, поэтому
рисунки уже добытых статей так не описать — только новых (или после повторной
добычи с `--force`).

## 3. Поиск — все ключи

```
.venv\Scripts\python -m georag.index.cli search "гидротермальные изменения ASTER" --limit 10 --per-doc 2 --year-from 2015
```

| Ключ | Зачем |
|---|---|
| `--limit 10` | сколько результатов показать |
| `--per-doc 2` | не больше N кусков одной статьи (0 — без ограничения) |
| `--year-from 2015` | только статьи не старше указанного года |
| `--source openalex` | искать только по одному источнику |
| `--candidates 50` | сколько кандидатов брать из каждого поиска до объединения |
| `--min-similarity 0.45` | отсечь непохожее: 0.45 — обычно, 0.55 — строго, 0 — показывать всё |
| `--require-words` | только куски, где буквально есть все слова запроса |

Векторный поиск всегда возвращает ближайшее — даже когда подходящего в базе
нет. Поэтому есть порог `--min-similarity`. У BGE-M3 текст про то же самое
даёт похожесть примерно от 0.6, случайный сосед — около 0.3–0.45. Куски, где
буквально есть все слова запроса, проходят порог всегда.

У каждого результата написано, **кто его нашёл**: «вектор» — по смыслу,
«текст» — по точным словам, «оба» — согласились оба способа. «Оба» — самый
надёжный признак.

## 3а. Страница в браузере

```
python georag.py web
```

`http://localhost:8000`, три вкладки: **Поиск**, **Статьи**, **Чат-бот** (под
ним — граф связей). Модель векторов грузится один раз при запуске, поэтому
поиск отвечает мгновенно. Остановить — Ctrl+C в том же окне. Страница слушает
только этот компьютер: из сети к ней не подключиться.

Другой порт — `.venv\Scripts\python -m georag.web.server --port 9000`.
Другая модель — в `docker-compose.yml` (сервис `llm`), и то же имя — в `--model`.

### Чат-бот

Под ответом — **«Связи из графа»**: что граф выписал из фрагментов, на которые
ссылается ответ. Щелчок по имени — оно на вкладке графа со всеми своими связями
(дальше можно ходить по соседям), по номеру [n] — сам фрагмент. В Телеграме — кнопка
«Связи» под ответом.

Как он отвечает, по шагам:

1. Qwen3 разбирает вопрос. Составной («какие признаки и какими методами их
   выделяют») делится на части, до трёх; на каждую — 3 поисковых запроса,
   по-русски и по-английски. Ищется и сам вопрос. Вопрос вдогонку
   («а по ASTER?») модель дописывает до самостоятельного — с предметом из прошлого.
2. **Поиск вместе с моделью.** Поиск приносит кандидатов с запасом (до 16 на
   вопрос, по 8 на часть составного, мягкий порог), Qwen3 **читает всех** пачками
   **и берёт только подходящие** —
   похожее по словам, но о другом, отбрасывает. Если чего-то не хватает, модель
   сама составляет новые запросы и ищет ещё — до трёх кругов. Для ответа — до 8
   фрагментов, не больше 3 из одной статьи; у каждой части вопроса свои места.
   Под ответом видно: сколько фрагментов прочла модель, сколько было кругов, чего
   не хватало и что искалось ещё. Если модель не отвечает — фрагменты берутся по
   близости, как в обычном поиске.
   - **«Что известно о …»**, «перечисли всё про …» — ответ собирается из
     датасета: фрагмент [1] — все факты о предмете вопроса из графа знаний,
     за ним — фрагменты, откуда взяты цитаты главных фактов. Предмет может быть
     любым — место, метод, процесс. Нужен построенный граф (`python georag.py graph`).
   - **Вопросы о связях** — «с какими минералами связано золото», «с чем
     ассоциирует хлорит», «что сопровождает оруденение», «где встречается …» —
     и «что известно о …» — **сбором по статьям**: модель читает до 30 статей, где
     предмет упомянут, и из каждой выписывает (с цитатой), с чем он связан;
     спросили о минералах — только минералы. Ответ — обзор по выпискам и полный
     перечень «Ещё в статьях базы» с номерами статей. Первый вопрос о предмете —
     1,5–2 минуты (статьи читаются), повторный — быстрее: выписки хранятся. Для
     частых предметов их готовит заранее ночной прогон (`collect`). Предмета нет
     ни в одной статье — ответ из датасета графа. Остальные вопросы идут поиском.
   - **Вопросы о самом наборе статей** — «сколько статей про …», «перечисли статьи
     про …», «какие статьи Петрова есть в базе», «статьи за 2020–2023 о …» — идут не по
     8 фрагментам, а по всей базе (`chat/catalog.py`). Модель при разборе называет тему
     основами слов на разных языках (France, French, Франц), годы и фамилию автора
     латиницей; дальше считает код: статья засчитывается, если тема есть в названии или
     хотя бы в 2 кусках текста. Ответ — «**В базе знаний N статей о теме …**», сколько
     по названию и сколько только по тексту, что искалось, и нумерованный список (до 60
     статей, больше — числом) с годом, авторами и пометкой «в названии» или «в тексте,
     кусков: k». Счёт по словам: статья, где тема названа иначе, не учтена. Вопрос о
     содержании статей («какие методы используют», «к каким выводам приходят») —
     обычным поиском.
3. **Нашлось** — Qwen3 пишет ответ только по этим фрагментам и после каждого
   утверждения ставит номер фрагмента. Номера сверяются: ссылка на фрагмент,
   которого модели не давали, зачёркивается. Говорит ли фрагмент то, на что он
   приведён, сверяет ещё один вызов модели (числа — код): утверждение, которого его
   фрагмент не подтверждает, убирается и показывается под ответом отдельно —
   «Утверждений, которых не подтверждают их фрагменты, убрано: N». Под ответом —
   источники, что искал бот и сколько утверждений подкреплены номером фрагмента.
4. **Не нашлось** (или модель прочла фрагменты, а ответа в них нет) — статьи
   не показываются. Бот пишет: «По вашему запросу в базе знаний такой
   информации нет» и предлагает спросить иначе — другими словами, с терминами
   по-английски. Ответа из общих знаний модели по умолчанию нет: даже с пометкой он
   вредит — модель уверенно сочиняет геологию места, о котором в базе ни слова.
   Включить его — переменная **`GEORAG_GENERAL=1`** (`1`, `true`, `yes`, `да`; пусто
   или другое — выключено): тогда ниже отказа — ответ модели с пометкой «ответ
   модели, не из базы знаний», без ссылок на статьи.
   Если вопрос вообще не о геологии («как испечь хлеб?») — только короткий отказ,
   при любом `GEORAG_GENERAL`.

Размышления вслух у Qwen3 выключены — ответ в разы быстрее.

**Статьи на китайском и японском.** Русский и английский запрос до них не дотягивается:
вектор русского вопроса ставит китайскую статью ниже случайных английских. Если в базе
такие статьи есть, задайте языки переменной **`GEORAG_TRANSLATE`** через запятую —
`GEORAG_TRANSLATE=по-китайски,по-японски`. Тогда при разборе модель пишет ещё и суть
вопроса коротким запросом на этих языках, и по нему ищется своя небольшая добавка — 6
кандидатов сверх основных; переводы видны среди запросов в «Искал». Пусто или не задано
— правила нет вовсе, разбор как раньше.

**Настроек у ответа нет.** Нужно подробно, кратко, списком, таблицей — так и
напишите в вопросе: «подробно: какие признаки…», «кратко — чем выделяют узлы?».
Не сказали — ответ по существу: вывод и главное списком.

Числа — в начале файлов `georag\chat\`: `settings.py` (сколько запросов и
фрагментов), `retrieval.py` (сколько кругов поиска, мягкий порог), `search.py`
(порог близости), `messages.py` (правила для модели, сколько прошлых реплик
помнить).

Из терминала — один вопрос, без разговора:

```
python georag.py ask "какие признаки гидротермальных изменений видны на ASTER?"
```

## 3б. Граф знаний и словарь синонимов

### Как строится

```
python georag.py graph --limit 30     проба: 30 фрагментов
python georag.py graph                все новые фрагменты
python georag.py graph --redo         всё заново — после правки правил
python georag.py graph --new          что нашла модель и почему код отбрасывал
```

Qwen3 читает фрагменты статей и выписывает **факты**: «от — связь — к».
«Билляхская зона — входит в — Анабарский щит». Предложения фрагмента
пронумерованы, и модель указывает номер предложения, где факт сказан, — цитатой
становится само это предложение. Переписывать цитату модели не нужно: ответ
вдвое короче, а цитата всегда дословная. Сущности — как их назвала статья
(место, метод, процесс — без разделения на виды), на языке статьи; связь —
по-русски, 1–4 слова. Правила для модели — `config\graph-rules.txt`, правятся
Блокнотом (сохранять в UTF-8); после правки — `graph --redo`.

Каждый факт **проверяет код**: в предложении должны быть видны оба конца факта
(с любыми окончаниями); если название стоит предложением выше («This area…»),
цитата — оба предложения. Не прошло — в граф не попадает. Выдуманные названия,
названия, дописанные «по смыслу», и общие имена без названия («this study»,
«predictive model», «работа [33]») так отсекаются. Затем каждый факт сразу же
**проверяется вопросами по цитате** (подробно — ниже, «Подтверждение»).
`graph --new` показывает, какие сущности и связи получились и почему код
отбрасывал остальное.

**Скорость.** У модели сразу 8 фрагментов (`--workers 8`, или переменная
`GEORAG_WORKERS`), и vLLM считает их одной пачкой. На RTX 5070 Ti выписать факты и
проверить их вопросами — 1,3 с на фрагмент (замер на 40 фрагментах, 12.10.2026);
на Ollama с 4 запросами сразу было 2,3 с, и вся база (4272 фрагмента) строилась
2 ч 44 мин (7334 подтверждённых факта, `.local/logs/graph-speed-20261010`).

**Новые статьи граф не пересчитывают.** Модель проходит только фрагменты, которых
ещё не видела, а готовый граф в памяти (страница, чат-бот, датасеты) дописывается
новыми фактами, без сборки с нуля. Всё заново — только `graph --redo` после правки
правил; с нуля собирается и граф в памяти после правки словаря синонимов.

Прервать можно в любой момент (Ctrl+C) — та же команда продолжит с того же места.
Нужна модель: `graph` поднимает её сам.

### Словарь синонимов

`config\synonyms.yaml` — разные написания одного и того же сводятся к одному
имени:

```
имена:
  Донецкий бассейн: [Donetsk basin, Донбасс, Donbass]
связи:
  приурочено к: [приурочен к, associated with]
```

Первое — как показывать, в скобках — как ещё пишут. Падеж и число не важны:
«Донецкого бассейна» узнаётся само. Чего в словаре нет, в граф идёт как написала
модель. Сюда — только настоящие синонимы (перевод, сокращение, другое
написание); «random forest» и «машинное обучение» — не синонимы, это факт.

Правка действует **сразу**: модель заново проходить не нужно, страницу — просто
обновить, бота перезапускать не надо.

Пополнять словарь помогает модель:

```
python georag.py synonyms
```

Она находит похожие имена (векторы BGE-M3) и по парам решает, одно ли это.
Предложения — в `.local\synonyms-предложения.yaml`, в том же виде, что словарь.
Откройте Блокнотом, нужные строки перенесите в `synonyms.yaml`, ошибочные — просто
не переносите. Сама модель словарь не правит. Строже или мягче —
`.venv\Scripts\python -m georag.graph.cli synonyms --threshold 0.85` (обычно 0.8;
выше — меньше предложений).

### Автосинонимы: одно и то же, записанное чуть иначе

```
python georag.py graph --names          новые имена графа — к уже известным
python georag.py graph --names --redo   все имена заново (после правки правил)
```

Модель пишет одно и то же по-разному: «Landsat8 OLI» и «Landsat-8 OLI»,
«mineralised zones» и «mineralized zones», «рудопроявление Эльвенейское» и
«Эльвенейское рудопроявление». Это сводится **само**, без словаря: имя каждой
сущности графа превращается в вектор, новое имя сравнивается с пятью ближайшими
уже известными (через индекс, не со всеми), и при похожести от 0,95 становится
их написанием. Идёт само после `graph` и проходит только новые имена — 9439 имён
с нуля считаются около 80 с.

Слить похожее, но разное не дают правила кода: разные числа («JCBN50» и
«JCBN45»), стороны и степени («Восточное» и «Западное рудное тело», «high thorium
and low uranium» и «high uranium and low thorium»), разные собственные имена.
Проверено 11.10.2026: из 74 слитых пар ошибочных нет, правила остановили 18.

Переводы и сокращения («золото» — «gold», «PCA») так не сводятся: у них похожесть
векторов в среднем 0,70 — для них остаётся словарь, и **словарь главнее**: имя из
`synonyms.yaml` автосинонимы не трогают. Похожие от 0,85 до 0,95 сами не
сливаются — там одно и то же лишь в половине пар; их предлагает `synonyms`.
Что слито, видно в таблице `entity_names` (колонка `canon` — чьё это написание).

### Датасеты

```
python georag.py dataset                     у чего больше всего фактов
python georag.py dataset "Анабарский щит"    все факты о нём, файл CSV для Excel
```

Датасет есть у любой сущности: все факты о ней — с чем и как связана, в скольких
статьях, цитата и статья. Факты о том, что в неё **входит** (по фактам «входит
в»), тоже попадают: датасет щита включает его зоны. Таблица кладётся в
`.local\datasets`. То же — в карточке узла на графе и в Телеграме (/dataset).

Готовых датасетов нет: каждый собирается из фактов в момент, когда его
открывают. Новый `graph` — новые сущности и их датасеты появляются сами.

### Граф на странице

Под чат-ботом — все факты одной сетью, как граф в Obsidian: сущности (синие) и
статьи (серые). Стрелка — факт, по направлению связи; тонкая линия — от статьи к
сущностям, о которых в ней факты. Колесо — масштаб, тянуть фон — сдвиг. Щелчок
по сущности — её датасет: строки фактов, нажатие на строку — цитата и кнопка
статьи; «Спросить чат-бота» — вопрос «что известно о …». Щелчок по статье — о
чём в ней факты и «Разбор статьи целиком».

### Адреса

Сервер — тот же, что открывает `python georag.py web` (`serve` — без браузера).

| Адрес | Что отдаёт |
|---|---|
| `GET /api/network` | сеть: сущности, статьи, факты с цитатами |
| `GET /api/datasets` | у каких сущностей больше всего фактов |
| `GET /api/dataset?name=Анабарский щит` | датасет сущности; `&format=csv` — таблицей; POST — то же JSON в теле |
| `GET /api/figure?id=12` | картинка рисунка (JPEG) по id в таблице рисунков |
| `POST /api/chat` | ответ чат-бота строками JSON; после `done` — `figures`: рисунки процитированных фрагментов |

С другой машины — только через SSH-туннель.

## 4. База в Docker

```
docker compose up -d          # поднять (первый раз — создаёт)
docker compose stop           # остановить, данные остаются
docker compose ps             # что сейчас работает
docker compose logs db        # что пишет база, если не поднимается
```

**Никогда:** `docker compose down -v` — удаляет том с базой, и всё придётся
загружать заново.

Перезагрузить всё в базу с нуля, не трогая добытые статьи:

```
python georag.py ingest --force
```

Граф при этом сохраняется: факты стираются только у фрагментов, чей текст поменялся,
и следующий `python georag.py graph` пройдёт их заново.

## 5. Языковая модель (vLLM)

Языковая модель — Qwen3-14B, сжатая до 4 бит (`Qwen/Qwen3-14B-AWQ`), в **vLLM** — в
Docker рядом с базой. Она пишет ответы чат-бота, выписывает факты графа
(`graph`, `synonyms`) и отбирает статьи. Векторы считаются без неё (BGE-M3 в самом
приложении).

```
python georag.py start        поднять базу и модель (в первый раз скачает ≈ 19 ГБ)
python georag.py status       что работает и отвечает ли модель
python georag.py stop         остановить базу и модель — видеокарта свободна
docker logs georag-llm        журнал модели: почему не поднялась
docker stop georag-llm        остановить только модель (база работает)
```

`web`, `ask`, `graph`, `eval` поднимают модель сами, если она не запущена. Модель
грузится 1–2 минуты (первый запуск — дольше: vLLM собирает свои ядра под видеокарту);
поиск в это время уже работает.

Настройки — в `docker-compose.yml`, сервис `llm`: модель, окно (`--max-model-len
12288`, то же число, что `NUM_CTX` в `georag/llm.py`), доля видеопамяти
(`--gpu-memory-utilization`). Имя модели для проекта — `qwen3-14b`
(`--served-model-name`). Адрес — переменная `GEORAG_LLM` (по умолчанию
`http://127.0.0.1:8100`; на 8000 — веб-страница): если модель работает на сервере,
задайте его, например `setx GEORAG_LLM http://сервер:8100`. Говорит проект с моделью по протоколу OpenAI
(`/v1/chat/completions`), так что сервер можно сменить (llama.cpp, SGLang), не
трогая код.

### Несколько пользователей и видеокарта на 16 ГБ

vLLM сам собирает одновременные запросы в одну пачку. Страница и Телеграм-бот
стоят в одной очереди (`georag/turns.py`): до 4 ответов сразу (переменная
`GEORAG_PARALLEL`), остальные ждут по порядку прихода и видят своё место. Граф —
8 фрагментов. Каждый запрос к модели ещё и берёт место в бюджете токенов
(`georag/llm.py`, `Budget`): сколько памяти под окна у vLLM, проект узнаёт из его
`/metrics` (или из переменной `GEORAG_KV_TOKENS`) и не шлёт больше, чем помещается, —
иначе vLLM вытесняет запросы, и они падают по таймауту. Соединения с базой — из пула
(переменная `GEORAG_DB_POOL`, по умолчанию 10). Сколько реально считается
одновременно, решает память под окна. Замер 12.10.2026, RTX 5070 Ti 16 ГБ:

- модель занимает 9,4 ГБ, служебная память vLLM — около 2 ГБ, под окна остаётся
  13 600 токенов (окна — в 8 битах, `--kv-cache-dtype fp8`). Это одно полное окно
  или 2–3 обычных задания чат-бота (5–7 тыс. токенов);
- рядом свободно около 3 ГБ — модели векторов этого мало: вместе с ней память
  кончалась, Windows гоняла её через общую, и vLLM писал 20–35 токенов в секунду
  вместо 76. Поэтому, пока работает vLLM, векторы сами считаются на процессоре:
  вопрос — 60 мс вместо 25, это незаметно. Загрузка статей на процессоре медленная
  (2,4 фрагмента в секунду вместо 190) — большую загрузку делайте при остановленной
  модели: `docker stop georag-llm`, `python georag.py ingest`, `docker start georag-llm`;
- один запрос: читает 2680 токенов в секунду, пишет 76 — как Ollama (3000–3400 и
  72). Одинаковое начало заданий не перечитывается (кэш начала);
- граф: 1,3 с на фрагмент при 8 сразу против 2,3 с на Ollama;
- чат-бот, один пользователь, 29 вопросов оценки: медиана 25,8 с, 95 % — до 35,6 с
  (на Ollama 25,4 и 34,6 с);
- чат-бот, несколько человек сразу (каждый ждёт свой ответ):

| сколько спрашивают | vLLM | Ollama (11.10.2026) |
|---|---|---|
| один | 27 с | 24 с |
| двое | 34 и 40 с | 36 и 47 с (2 слота — 36 и 37 с) |
| четверо | 37, 41, 44 и 49 с | 4 слота не помещались — 143 с |

**На сервере выигрыш больше**: там под окна десятки гигабайт — на одной карте 48 ГБ
(L40S) около 30 одновременных заданий, по оценке 340–840 вопросов в час; на 80 ГБ
(A100) — 590–950 (оценки, мерить на месте). На сервере уберите из
`docker-compose.yml` строки `--max-num-seqs` и `--max-num-batched-tokens` (они
ужимают vLLM под 16 ГБ); модель векторов там поместится на той же карте.

На 16 ГБ без `--max-num-seqs=8 --max-num-batched-tokens=2048` vLLM не запускается:
служебная память под сотни запросов сразу съедает всё место под окна («No available
memory for the cache blocks»).

## 6. Проверка и логи

### Оценка базы и чат-бота

```
python georag.py eval                  поиск и ответы по вопросам config\eval-questions.yaml
python georag.py eval --only-search    только поиск — если модель не работает
python georag.py eval --only s01,t01   отдельные вопросы
python georag.py eval --no-graph       то же без графа: сравнить с обычным прогоном, что граф даёт ответам
```

Отчёт — `.local\logs\eval-<дата>.md` (открывается Блокнотом) и `.json`. В начале отчёта
итог и сравнение с прошлым прогоном, дальше таблица по вопросам и разбор того,
что не прошло: не нашлось, нет ключевого, короткий ответ, мало ссылок, ответил
по базе на вопрос не по теме. Раздел «Где базе не хватает статей» — по каким вопросам
добрать темами `topics-check.yaml`.

Свои вопросы добавляются в `config\eval-questions.yaml` — формат описан в начале
файла. Лучше всего работают вопросы, ответ на которые вы сами знаете по статьям.
